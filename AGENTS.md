# Repository Guidelines

## Project Structure & Module Organization

- `Фронт/smart_energy/`: React 19 / Vite 8 frontend using React Router 7 and Recharts 3. Routes live in `src/app/`; screens in `src/pages/`, including `dashboard/`, `aggregation/`, and `notifications/`; HTTP clients in `src/features/*/api/`; auth state in `src/features/auth/model/`; shared API configuration and themes in `src/shared/`; charts in `src/components/charts/`. The dashboard's `DeviceAvailabilityPanel.jsx`, `availabilityUtils.js`, and `deviceAvailability.css` implement the independent device-data report. Static assets belong in `public/`; shared styles include `src/*.css`.
- `Бэк/project_backend/`: Django 5.1 / Django REST Framework gateway. `config/` contains settings, routing, and runtime secret management. `apps/users/` handles the custom user, JWT cookies, and admin; `apps/consumption/` contains dashboard SQL, views, the analytics client, and the read-only adapter proxy `availability_views.py`; `apps/aggregation/` proxies staff-only adapter management. `apps/notifications/` contains opt-in notifications and hourly comparison curves. Tests include `tests.py`, `test_*.py`, and `apps/users/test_admin.py`. Component architecture decisions are in `docs/adr/`.
- `Аналитический сервис/Analytical_service/`: FastAPI period-comparison service. `app/api/` contains routes, `app/schemas/` validation, `app/services/` statistical calculations and Z-table lookup, `app/db/` PostgreSQL access, `app/core/` settings and internal authentication, and `app/data/` the standard-normal CSV table. Tests live in `tests/`.
- `adapter/`: PostgreSQL ingestion/aggregation package and private HTTP service. `__main__.py` exposes the CLI; `mapping.py` validates source profiles and column mappings; `model.py`, `queries.py`, and `runner.py` build and replace aggregates; `schema.py` implements explicit additive target upgrades; `store.py` persists profiles, jobs/events, schedule, and day results; `service.py` runs the API, writer worker, and scheduler. `live.py` reads completed current-day hours for notifications. `availability.py` has a separate read-only background reader and in-memory caches for device diagnostics; it never uses the writer queue. `local_setup.py` explicitly prepares an isolated workstation control schema. `profiles/` contains example profiles; `tests/` includes unit, integration, HTTP, and isolated Compose checks. It uses the Python standard-library HTTP server, not FastAPI.
- Root `docker-compose.yml` runs frontend, backend, and `analytical`; `docker-compose.adapter.yml` adds the adapter and gateway configuration. `agg_taables.sql` describes existing aggregate tables; it is not a Django migration or an automatic setup step.
- `docker-compose.vm42.yml` is a standalone deployment for `.42` with a dedicated PostgreSQL 17 container and source SSH tunnel to `.50`; `docker-compose.vm42-access.yml` runs on the PC for external access through SSH. Root `README.md` explains internal HTTPS and external SSH access; `deploy/vm42/README.md` covers installation. VM services use host networking with loopback ports 25433 (new database), 25432 (source tunnel), 15000 (Django), and 18001/18002 (analytics/adapter). HTTPS listens on 8443; `deploy/vm42/https-allow.conf` temporarily ends with `allow all` at the user's request, so network firewall rules must enforce external SSH-only access. Specific allow rules are retained: replacing the final directive with `deny all` restores source IP filtering and preserves loopback SSH forwarding. The listed institute networks are the observed VM subnets; additional workstation networks require administrator confirmation when restoring filtering. Do not combine these files with local application Compose files or replace the VM's existing PostgreSQL 10/CMDBuild deployment.

Use root `README.md` for the Docker quick start, `deploy/LOCAL_DEPLOYMENT.md` for deployment and frontend packaging, `DATABASE.md` for database contracts, `SOURCES_AND_AGGREGATIONS.md` for the operator workflow, and `adapter/README.md` for adapter configuration and validation. Component READMEs and ADRs include older proposals; verify behavior against current code, dependency manifests, and Compose files before relying on them.

Root `spec.md`, `plan.md`, and `tasks.md` cover available-data aggregation and the weekly graph. The device report has separate approved SDD documents in `docs/specs/device-data-availability/`: `spec.md`, `plan.md`, `tasks.md`, `ui.md`, and `DEPLOYMENT.md`. Keep these feature scopes distinct. `deploy/vm42/AGGREGATION_UPDATE.md` covers writer/control upgrades; the device report's deployment guide covers its own configuration and needs no new migrations. Local implementation and verification do not establish that the VM has been updated.

## Architecture & Data Flow

- `apps/notifications/` is an additive Django app with personal opt-in settings, daily report snapshots, and SMTP delivery. `run_notifications` runs in a separate Compose service using the backend image. Legacy rules read daily aggregates and use at least 7 complete days in 30 days. Configurable curves read hourly aggregates and can obtain completed current-day hours from adapter `/live-hours`; they use N matching prior days or a fixed range, mean/median/date-based linear trend, and day-type grouping. Preserve two-sided comparison, Moscow day/hour boundaries, and isolation through `rule_enabled` and `configuration_key`. Never substitute `available_energy_kwh` for full energy or change writer formulas for alerts. Reports are unique per user/day; ambiguous SMTP submissions must not be blindly retried. SMTP secrets belong in private env files. See `NOTIFICATIONS.md` and `NOTIFICATION_CURVES.md`.

- The browser calls Django under `/api/`; Vite proxies that prefix in development. Container Nginx terminates HTTPS, serves the SPA, and proxies `/api/`, `/admin/`, and `/static/` to Django. Django serves admin assets through WhiteNoise.
- `/api/auth/` provides registration, login, refresh, profile, and logout. Keep access tokens in the existing in-memory auth store and refresh tokens in HttpOnly cookies. Reuse feature clients, `buildApiUrl`, and the shared refresh flow; preserve `credentials: 'include'` and the single retry after a 401.
- Most `/api/consumption/dashboard/` endpoints read PostgreSQL directly through Django SQL helpers. The exception `/api/consumption/dashboard/device-availability/` proxies the adapter's private `/device-availability` reader and is available to every authenticated user. `/api/consumption/analytics/period-comparison/` resolves filters in Django and calls FastAPI's `/internal/analytics/period-comparison` through `httpx`; FastAPI reads hourly aggregates and performs the Z-test. It does not persist analysis results.
- `/api/aggregation/` forwards an allowlisted set of operations to the adapter with `X-Internal-Token`. Management operations require `is_staff` via DRF `IsAdminUser`; the capabilities endpoint is available to authenticated users. Keep server-side permission checks even when the UI hides controls.
- Django uses three database aliases: `default` for ORM/auth tables in `student` (default search path `student_schema,public`), `source` for metadata in `paradigm_db`, and `analytics` for hourly/daily aggregates in `student`. FastAPI reads aggregates via psycopg 3. The adapter writer reads raw `paradigm_db.public.electricity_sensor_readings` and replaces hourly/daily tables in `student_schema`. Its independent availability reader also reads `public.climate_sensor_data` and `public.meteo_sensor_data`. Control state uses `adapter_control` by default or an explicitly configured isolated schema.
- Application Compose uses external PostgreSQL, normally reached through an SSH tunnel at `127.0.0.1:15432` on the host and `host.docker.internal:15432` in containers. It does not provision PostgreSQL, source metadata, or aggregate tables. Django migrations create ORM tables; `adapter init-control` separately installs the adapter control schema.

## Build, Test, and Development Commands

Run component commands from their component directory; run `python -m adapter` and Compose commands from the repository root. Quote paths containing spaces/Cyrillic names. Keep Markdown and source files in UTF-8; in Windows PowerShell use `Get-Content -Encoding UTF8` when reading them.

### Local Development

- Frontend: use Node.js 22.12+ (the locked Vite version supports `^20.19.0 || >=22.12.0`). `npm ci` installs locked dependencies; `npm run dev` starts Vite at `127.0.0.1:5173`; `npm run build` creates `dist/`; `npm run lint` runs ESLint; `npm run preview` serves the build.
- Python: create/activate a virtual environment and run `python -m pip install -r requirements.txt` for the relevant component. Backend and analytics Docker images use Python 3.11; adapter and integration-test images use Python 3.12. Dependencies are maintained per component, not in a root requirements file. Django uses DRF, SimpleJWT, psycopg, httpx, Gunicorn, and WhiteNoise; analytics uses FastAPI, Uvicorn, Pydantic Settings, and psycopg; adapter runtime dependencies are psycopg and tzdata.
- Backend: `python manage.py migrate` applies ORM migrations; `python manage.py runserver 127.0.0.1:5000` starts the gateway; `python manage.py createsuperuser` creates an administrator. Use migrations for ORM changes, not to recreate externally managed energy tables.
- Analytics: `uvicorn app.main:app --host 127.0.0.1 --port 8001 --reload`; `/health` is the health endpoint.
- Adapter: `python -m adapter init-control` installs control tables once; `python -m adapter serve` runs the private service (default port 8002). For CLI syntax, use `python -m adapter --help`. Local adapter commands do **not** load `.env` automatically: export the required variables in the shell. A refresh without `--apply` is a dry-run; do not add `--apply` just to validate changes.

### Docker & Frontend Packaging

Follow root `README.md` to configure environment files, the SSH tunnel, and both TLS files (`ssl/nginx.crt`, `ssl/nginx.key`) before starting. The standard application URL is `https://localhost`; backend and analytics are bound to host loopback on 5000 and 8001. Adapter port 8002 is internal only.

```powershell
docker compose -f docker-compose.yml -f docker-compose.adapter.yml build
docker compose -f docker-compose.yml -f docker-compose.adapter.yml run --rm --no-deps adapter init-control
docker compose -f docker-compose.yml -f docker-compose.adapter.yml run --rm --no-deps adapter upgrade-aggregates
docker compose -f docker-compose.yml -f docker-compose.adapter.yml run --rm --no-deps adapter upgrade-control
docker compose -f docker-compose.yml -f docker-compose.adapter.yml up -d
docker compose -f docker-compose.yml -f docker-compose.adapter.yml ps
```

`init-control` is a first-install step. `upgrade-aggregates` explicitly adds metric counters and nullable `available_energy_kwh`; legacy values/counts remain unverified until refresh. Existing installations also need explicit `upgrade-control` to control schema version 2 before the new service starts. `serve` checks the schema version and does not initialize it. To run without the adapter, use `docker compose up -d --build`; aggregation management and device availability need the overlay. Backend startup waits for PostgreSQL and, in application Compose, applies migrations and runs Gunicorn. Energy index creation is disabled there (`RUN_ENERGY_INDEXES=0`); do not enable DDL as a routine startup fix. Preserve the `django-secret` volume when stopping: it holds the persistent session/JWT signing key; ordinary `down` should not use `-v`.

The base/VM frontend Dockerfile unpacks the tracked `frontend-dist.tar.gz`; it does **not** build React sources. Workstation `deploy/local/Dockerfile.frontend` instead builds sources with Node 22, but this does not update the archive needed for VM delivery. After a UI change, run checks, build with `VITE_API_URL=/api`, and refresh the archive from inside `Фронт/smart_energy/`:

```powershell
$env:VITE_API_URL = '/api'
npm run build
tar -czf frontend-dist.tar.gz -C dist .
```

Include the updated archive with UI source changes intended for Docker deployment, then rebuild the frontend image. Keep loose `dist/`, `node_modules/`, and `staticfiles/` out of commits.

## Coding Style & Naming Conventions

Use four-space Python indentation, `snake_case` functions/modules, and `PascalCase` classes. Follow existing React code: two-space indentation, single quotes, and omitted semicolons. Components use `PascalCase.jsx`; helpers use `camelCase.js`. Keep HTTP logic in feature API modules and shared URLs in `src/shared/api/config.js`. ESLint flat configuration enforces JavaScript, React Hooks, and React Refresh rules; no Python formatter is configured. Follow surrounding Python quote style rather than reformatting unrelated code.

For SQL, bind values as parameters and validate/quote dynamic identifiers using existing helpers or `psycopg.sql.Identifier`. Never accept arbitrary SQL or connection strings from browser input; adapter profiles refer to server-defined connection aliases.

## Aggregation & Energy Contracts

- Source readings and metadata are read-only. Refreshes replace all rows for each selected day in **both** existing aggregate tables in one transaction per day, protected by target locks. Preserve rollback, idempotency, and retry/progress behavior; different source profiles cannot safely merge independent data into the same target day.
- Ranges are `[from, to)` in the configured timezone; unfinished/current and future days are excluded. Keep the Moscow output/calendar conventions. Explicitly interpret timezone-naive source timestamps through `source_timezone`.
- Profiles are versioned and require confirmed mappings, units, and sampling interval. Preserve successful preview before apply/activation, the fresh source-schema and directory signatures, and separate schedule enablement. Duplicates, low coverage, irregular cadence, and fewer points are warnings rather than reasons to reject a whole day. Required schema/key errors, ambiguous mappings, and unknown sensors remain integrity failures; do not bypass them to make a job succeed.
- Only timestamp and meter ID are required source mappings. Missing/unreadable optional measurement columns produce NULL and schema warnings; an existing mapped column of the wrong type is an error. Missing required columns, NULL timestamps (checked across the source), and blank/NULL IDs in the requested range stop refresh before replacement. Total power needs its total reading or all three valid phases; partial phases remain individual measurements. Manual apply requires the schema signature from a fresh successful preview. See `adapter/REVIEW.md` for the checked scenarios and limitations.
- Exact duplicate readings have no extra weight; conflicting readings at one meter/timestamp are averaged before 10-second windows. Do not combine partial phases from different records into synthetic total power. The 10-second window is separate from the confirmed source sampling interval (for example, 5 seconds). `points_count` and metric counts represent unique timestamps and their own valid values, not number of windows. Preserve per-metric weights through daily rollup.
- For each successfully read day, materialize 24 hourly rows and one daily row per expected name from the profile directory, including devices with no source rows. Empty metrics/energy remain NULL and counts are 0. A successfully read empty day can replace old values with NULL; a failed read must preserve old rows. The writer currently uses all names returned by the configured directory without type filtering. The availability report's all-device scope does not independently settle which devices belong in an electrical writer profile; do not silently restrict writer scope to observed senders or add a guessed name filter.
- Day-local quality/data/integrity/query-timeout failures produce `day_skipped` with rollback of that day's replacement, then continue to later days; infrastructure failures still fail the job. A job with some skipped days may succeed with warnings; if no day completes, it fails. Preserve per-day outcomes instead of relying only on the overall job status.
- Energy uses a confirmed measurement interval and normalized power units; never guess the interval or treat the old minute-based SQL formula as a reference for 5-second readings. Missing/invalid power can produce warnings for individual meters and `NULL` energy; a real zero remains zero. Preserve unknown energy in aggregate totals rather than converting it to zero or silently summing only known values.
- Aggregate means persist `<metric>_count` (hourly `METRICS`, daily `DAILY_METRICS`). Consumers must weight by these valid-value counts, never by `points_count` or a guessed legacy count. Run `upgrade-aggregates` explicitly before the new writer/API; VM `start.sh` stops adapter and notifications and runs the additive target upgrade plus `upgrade-control`. Legacy counters remain NULL until a validated refresh. Fingerprint/algorithm version 3 requires a compatible profile version and fresh preview. Weekly power averages each meter across time before summing meters; energy remains additive.
- `available_energy_kwh` stores only known power-duration contributions, bounded by the confirmed interval and next timestamp; it is not extrapolated over missing time. `energy_kwh` remains NULL unless full energy is known. Empty hours/days stay NULL rather than measured zero. Sum known available contributions separately; Django/analytics/notifications must never silently substitute them for full energy. Daily averages use metric counts; energy is additive.
- Power timeseries retain the strict full `value` and separately expose `available_value`, `available_meters`, and `total_meters`. The UI displays available power with explicit coverage instead of hiding all meters when one is missing; fully unknown points remain gaps and measured zero remains zero. Meter scope covers meters present anywhere in the filtered aggregate range; it cannot discover meters absent from the entire range. Energy totals remain strict. Test actual non-NULL chart values, not only HTTP status and point count.
- The main dashboard's 7-day power view uses exactly seven daily calendar positions: selected Moscow day and six preceding days. Preserve gaps and visible isolated points, including real zero; do not connect missing days or replace a missing last value with an earlier reading. Placeholder rows from refreshed days can expand aggregate meter scope; older days may have a different stored scope.
- Control schema v2 separates `attempted_until` (automatic scanning boundary) from `processed_until` (continuous successful progress). `day_results` stores the latest written/skipped outcome per profile/day; manual repair can close gaps. CLI checkpoint v2 also retains skipped dates and both boundaries. Explicit manual ranges must not silently initialize/advance automatic progress; checkpoint initialization is an explicit apply operation.
- Writer history is in control `jobs` and JSONB `jobs.events` (last 800 events/job); `day_results` is not an append-only audit. The UI/API job list returns the last 50 jobs. A matching stored successful preview can enable apply for the same profile and exact date range after the replacement checkbox; changing dates alone does not rerun validation. These logs do not preserve previous versions of aggregate rows.
- `ENERGY_USE_STORED_ENERGY` defaults to `0` (legacy consumption calculation). Enabling stored `energy_kwh` requires historical validation/recalculation and the same flag in Django and analytics. Follow the transition procedure in `adapter/README.md`; an adapter deployment alone does not switch consumers.
- The existing VM `.42` deployment completed this transition on 2026-10-31: both consumers use stored energy and the daily schedule is enabled. Legacy rows that could not be verified remain explicitly unverified. See `deploy/vm42/ADAPTER_UPDATE.md`; do not treat the original migration's disabled schedule/legacy flag as its current state.
- On 2026-11-06 VM42 was updated to algorithm 3/control schema 2 with its database container, volumes and private configuration preserved. A fresh validated VM profile completed actual daily and repeat scheduled jobs for 2026-11-05 (4344 hourly/181 daily rows); automatic scheduling remains enabled. See `deploy/vm42/RELEASE_20261106.md` for profile/job IDs, backup, build-only host-network overlay and checks. The PC's VM SSH access currently uses `https://localhost:8444/`, separate from workstation HTTPS on 8443. Historical gaps outside that refreshed day were not repaired.
- During that deployment the existing VM42 → VM50 source SSH tunnel intermittently lost connectivity and automatically reconnected; availability scans returned partial/unknown. A healthy container is only a point-in-time observation. Scheduled OperationalError failures retry up to five attempts at five-minute intervals, with old data/progress retained; this path has an isolated worker integration test. Do not claim external network reliability or a completed availability scan from writer success alone; consult the release record for the measured outcome.

Match `ENERGY_ADAPTER_TOKEN` in root `.env` and adapter environment; the adapter requires at least 24 characters and authenticates every HTTP request, including `/health`. Keep internal service tokens out of the browser.
- Adapter DSNs are server environment variables: `ENERGY_AGG_SOURCE_DSN`, `ENERGY_AGG_TARGET_DSN`, optional `ENERGY_AGG_DIRECTORY_DSN`, and optional `ENERGY_ADAPTER_CONTROL_DSN`. An explicit profile `directory_connection` wins; otherwise the dedicated directory reader is used when configured, falling back to the source connection. Additional source aliases come from `ENERGY_ADAPTER_CONNECTIONS`.
- Keep credentials, `.env*` except `.env.example`, TLS private keys/certificates, local databases, virtual environments, caches, checkpoints, and `energy_aggregation/` / `adapter/state/` out of commits. Do not print DSNs or secrets in logs, documentation, or test output. Use configured runtime secrets and HTTPS cookie settings for deployed Django rather than development defaults.
- VM private files (`deploy/vm42/app.env`, `.env`, `secrets/`, `ssl/`, `backups/`) are ignored. `configure.py` prepares these once without overwriting them; its tests run with `python -m unittest discover -s deploy/vm42 -p test_configuration.py`. The migration only reads `.50` and refuses to overwrite a populated target; copied legacy raw-table data is excluded. Preserve profile fingerprint validation: migrated profiles require a fresh version/preview before activation, and scheduling starts disabled.

## Device Availability Report

- The main dashboard's `DeviceAvailabilityPanel` is available to all authenticated users. It has independent day/week/month and problem-state selectors, search, type filter, and 10-row pages. Consumption/date/meter filters must not narrow this report or change its state. Keep polling/cancellation and ignore late responses of a previous period. Unknown assessments are shown separately rather than counted as proven silence or normal operation.
- Device scope is the entire directory with stable IDs and model/type joins, including devices that never sent a reading. The 2026-11-05 snapshot had 181 devices (153 electricity meters and 28 other devices); these are observations, not constants. Electricity, climate, and meteo use their own raw tables. Absence of electrical aggregates does not prove that another type has no readings. The report never runs refresh, changes schedules, writes aggregates, or fixes their historical scope.
- Periods are the last completed 1/7/30 Moscow days, `[start,end)`, ending at today's Moscow midnight. The preceding 30 days form the baseline and exclude the checked period. Deduplicate by device/timestamp; one usable retransmission makes that timestamp usable. Do not count packets/windows as independent measurements or merge different devices.
- **This report alone excludes NULL, non-finite values, and numeric 0 from usable measurements.** All-NULL/all-zero devices remain in the report as `no_data`; they are not removed from scope. Electricity uses total power first, falling back to all three valid phases of one record only when the total is unavailable; the resulting power must be finite and nonzero. Climate/meteo need any finite nonzero environmental measurement; service/battery fields alone do not qualify. Preserve valid zero in the consumption aggregates, graphs, analytics, and notification energy contracts.
- Automatic baseline: median of 30 daily usable-timestamp counts, including zero days, per device. A candidate needs at least 21 positive days within ±20% of that median. Match model and historical cadence (median of daily positive-timestamp-gap medians; NULL/0 packets still establish cadence), within 20% of the target cadence. At least three stable matching devices supply the median of their daily levels; otherwise use the target's own stable baseline, else no reference. Multiply the daily reference by period days. Positive count strictly below 90% is `low_data`; exactly 90% passes. Zero usable count is `no_data` even without a baseline; positive count without a reference is `unknown`. Do not infer physical health or time coverage from these relative counts, or normalize a device using its checked period.
- `availability_views.py` exposes only validated `period=day|week|month` and `refresh=0|1` through `/api/consumption/dashboard/device-availability/` with `IsAuthenticated`. It calls private adapter `/device-availability` using the server token. Keep `apps/aggregation/AdapterView` staff-only; do not expose general adapter operations, aliases, DSNs, or SQL to ordinary users.
- Configure a validated/current-fingerprint electricity profile via `ENERGY_AVAILABILITY_PROFILE_ID` or the active validated profile; an explicit ID does not activate the writer or schedule. IDs belong to a control namespace, so choose the VM's own profile on deployment. Climate/meteo default to `public.climate_sensor_data` / `public.meteo_sensor_data` in the source connection; server-only `ENERGY_AVAILABILITY_SOURCES` may override `table`, `connection` alias, and `source_timezone`. Directory access follows the electricity profile. See the feature deployment guide for measured fields and configuration.
