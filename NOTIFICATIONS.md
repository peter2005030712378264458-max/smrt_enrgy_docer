# Уведомления о суточном потреблении

Страница: **https://localhost:8443/notifications** через внешний SSH-туннель
или **https://193.232.208.42:8443/notifications** из разрешённой внутренней сети.
Ссылка «Уведомления» находится в меню дашборда и доступна всем вошедшим пользователям.

## Как пользоваться

1. Откройте «Уведомления». Проверьте адрес вашей учётной записи — на него идут письма.
2. Укажите критическое отклонение в процентах и включите проверку.
3. Нажмите «Сохранить настройки». Проверка работает в фоне; браузер можно закрыть.
4. В таблице «Мои отчёты» смотрите результат по дням и состояние отправки письма.
   В «Подробнее» показаны сохранённый порог, состав расчёта и причины недостатка данных.
5. Чтобы остановить мониторинг и новые письма, выключите флажок и сохраните настройки.
   Ранее созданные отчёты сохраняются.

По умолчанию функция выключена. Настройки и отчёты индивидуальны; пользователь
не может прочитать чужой журнал или изменить адрес назначения через API уведомлений.
Настройка порога действует на новые результаты; завершённые отчёты хранят прежний порог.

## Формула

Сравниваются завершённые сутки по Москве и среднее за предыдущие **30 календарных дней**.
Текущие сутки и сами проверяемые сутки в среднее не входят.

```text
отклонение, % = (энергия суток − средняя суточная энергия) / |средняя| × 100
```

Критическим считается рост или снижение, для которого абсолютное отклонение
достигает заданного порога. Например, при среднем 100 кВт·ч и пороге 30%
значения 130 и 70 кВт·ч критические, 120 кВт·ч — в пределах порога.

Используется полная сохранённая суточная энергия. Все участвующие счётчики
должны иметь известную энергию и подтверждённое число корректных измерений.
Для среднего берутся только полные дни с тем же составом счётчиков;
нужно минимум **7** таких дней в предыдущем 30-дневном окне.
Частичная сумма не выдаётся за полное потребление.

Если полной энергии или среднего нет, сохраняется отчёт «Недостаточно данных»
с объяснением. Тревожное письмо не отправляется. Среднее 0 и энергия 0 означают
нормальный результат; при среднем 0 и ненулевой энергии событие критическое,
но процент не определён и не подменяется произвольным числом.

## Фоновая обработка

Отдельный процесс `python manage.py run_notifications` проверяет данные раз в минуту.
При включении мониторинга первым проверяется вчерашний день — рассылки за всю
старую историю нет. Далее обрабатываются новые завершённые дни; после простоя
за один цикл догружается до 31 дня. Результаты с недостаточными данными повторно
проверяются в течение последних 7 дней, чтобы дождаться завершения адаптера.

Для пользователя и даты существует один отчёт. Успешно оценённый день повторно
не рассылается при перезапуске. Завершённые отчёты являются снимками;
позднейший пересчёт исходных агрегатов не переписывает их.
Перед отправкой повторно проверяется включение функции и активность пользователя.
Если письмо уже передано SMTP-серверу, последующее выключение не может отозвать его.

При ошибке подключения к SMTP — до пяти попыток с интервалом 15 минут.
Если процесс оборвался во время передачи и неизвестно, принял ли сервер письмо,
статус — «Доставка неизвестна», без автоматического повтора возможного дубликата.
Статус «Передано почтовому серверу» подтверждает принятие SMTP, а не попадание во входящие.

## Настройка почты

Нужен один почтовый отправитель: с него можно отправлять на Gmail, Mail.ru
и другие адреса зарегистрированных пользователей. В приватном `deploy/vm42/app.env`
задаются параметры предоставленного почтового сервера:

```dotenv
EMAIL_HOST=smtp.example.org
EMAIL_PORT=587
EMAIL_HOST_USER=alerts@example.org
EMAIL_HOST_PASSWORD=app-password-here
EMAIL_USE_TLS=1
EMAIL_USE_SSL=0
DEFAULT_FROM_EMAIL=alerts@example.org
```

Это пример, а не действующее подключение. Для сервера с SSL на 465 обычно
устанавливаются `EMAIL_USE_TLS=0` и `EMAIL_USE_SSL=1`; использовать нужно
параметры конкретного провайдера. Одновременно TLS и SSL включать нельзя.
Используйте отдельный ящик и пароль приложения/SMTP. Реальные значения не включаются в Git.

Если SMTP не настроен, отчёты продолжают создаваться, а страница показывает
предупреждение. Критические письма ожидают настройки отправителя.

## Развёртывание

На подготовленной ВМ, после загрузки новых образов backend и frontend:

```sh
cd /home/collective/smart-energy-vm42
sh deploy/vm42/start.sh
```

Backend применяет миграцию нового приложения. Она создаёт только собственные
таблицы настроек и отчётов; исходные данные и таблицы агрегатов не меняются.
Compose добавляет сервис `notifications`, использующий тот же образ, что backend,
но отдельную команду фоновой обработки. Сервис не публикует сетевых портов.

Для прежнего локального Compose добавлен отдельный overlay:

```sh
docker compose -f docker-compose.yml -f docker-compose.notifications.yml build backend frontend
docker compose -f docker-compose.yml -f docker-compose.notifications.yml run --rm --no-deps backend python manage.py migrate
docker compose -f docker-compose.yml -f docker-compose.notifications.yml up -d
```

При необходимости локального адаптера добавьте также `-f docker-compose.adapter.yml`.
Настройки SMTP должны находиться в используемом backend env-файле.

## Код и API

Основной код: [apps/notifications](Бэк/project_backend/apps/notifications).
Настройки и отчёты хранятся ORM в БД приложения. Суточные агрегаты читаются
через существующее подключение `analytics`, без обращения к сырью на `.50`.

| API, требуется авторизация | Назначение |
| --- | --- |
| `GET /api/notifications/settings/` | Личные настройки, адрес, состояние настройки почты и последняя проверка |
| `PATCH /api/notifications/settings/` | Поля `enabled` и `threshold_percent` (0.01–10000, до двух знаков после точки) |
| `GET /api/notifications/reports/?page=1` | Личные отчёты, по 20 на страницу |

Общий SMTP-транспорт не принимает адреса получателей из браузера.
Доступ к отчётам фильтруется по текущему пользователю на сервере.
