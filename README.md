# Smart Energy — запуск и доступ к сайту

Приложение и его база данных работают на **193.232.208.42**.
Сырые показания и справочники читаются с **193.232.208.50**.

| Кто открывает сайт | Адрес | Что нужно |
| --- | --- | --- |
| Сотрудник во внутренней сети | **https://193.232.208.42:8443** | Браузер и учётная запись приложения |
| Пользователь из внешней сети | **https://localhost:8443** | SSH-туннель к `.42` и учётная запись приложения |

Прямой HTTPS разрешён для обнаруженных сетей `193.232.208.32/27` и
`192.168.1.0/24`. Полный список сетей рабочих ПК пока не подтверждён.
Если сотрудник получает **403**, администратор должен добавить его фактическую
подсеть в `deploy/vm42/https-allow.conf`. Для остальных адресов прямой доступ
закрыт; через SSH можно подключаться из внешней сети.

## 1. Запустить приложение на ВМ

Подключитесь к ВМ:

```sh
ssh collective@193.232.208.42
```

Введите **SSH-пароль пользователя `collective`**. Затем **на ВМ** выполните:

```sh
cd /home/collective/smart-energy-vm42 && sh deploy/vm42/start.sh
```

Если приглашение терминала уже начинается с `collective@energy-cmdbuild2`,
вы находитесь на ВМ: повторно выполнять `ssh` не нужно.

Сценарий поднимает контейнеры приложения, новую БД и соединение с источником.
При повторном запуске существующие данные сохраняются. На текущей ВМ настройки,
образы и перенесённая БД уже подготовлены.

При обновлении сценарий также добавляет в агрегаты счётчики корректных
измерений. Данные не стираются. История пересчитывается отдельно после
проверки качества; для точной энергии оба сервиса используют проверенное
сохранённое `energy_kwh` (`ENERGY_USE_STORED_ENERGY=1`). Старый комплект
контейнеров дашборда после успешного обновления останавливается.

Обновление на `.42` выполнено 31.10.2026. Результаты проверки доступа и истории —
в [отчёте о развёртывании](deploy/vm42/ADAPTER_UPDATE.md).

Предупреждение о непроверенной истории означает, что старые агрегаты сохранены,
но их энергию или точные средние пока нельзя подтвердить по исходным показаниям.
Такие значения отображаются как «—». Остальные периоды доступны обычным образом.

Если мощность доступна только у части счётчиков, график показывает доступную
сумму с отметкой полноты, например «47 из 49». Отсутствие одного счётчика
не скрывает остальные. Полная энергия при недостатке измерений остаётся «—»;
причина указана рядом с показателем.

## 2. Открыть сайт внутри института

Откройте в браузере **https://193.232.208.42:8443** и войдите в приложение.
SSH и Docker на рабочем ПК для этого не нужны.

- Дашборд: `https://193.232.208.42:8443/dashboard`.
- Источники и агрегации: `https://193.232.208.42:8443/aggregation` — для персонала.
- Админка: `https://193.232.208.42:8443/admin/`.

Сертификат содержит IP сервера, но является самоподписанным. Для доступа без
предупреждений администратор должен распространить публичный сертификат
`deploy/vm42/ssl/nginx.crt` как доверенный либо установить сертификат внутреннего
центра сертификации. Приватный файл `nginx.key` сотрудникам передавать не нужно.

## 3. Открыть сайт из внешней сети

**На своём ПК**, в PowerShell или терминале, выполните:

```sh
ssh -N -L 127.0.0.1:8443:127.0.0.1:8443 collective@193.232.208.42
```

Введите SSH-пароль и оставьте терминал открытым. Команда после подключения
может ничего не выводить — это нормально. Откройте **https://localhost:8443**.
На странице вводится пароль приложения, а не SSH-пароль.
Остановить этот туннель можно сочетанием **Ctrl+C**.

Если на вашем ПК уже работает Docker-туннель и сайт открывается по этому адресу,
второй туннель запускать не нужно. Его можно запустить из корня проекта:

```powershell
docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml up -d --no-build
```

Вариант с Docker использует подготовленные приватные настройки и продолжает
работать после закрытия терминала. Он подходит для уже настроенного ПК;
обычному внешнему пользователю достаточно команды `ssh` выше.

## Как устроено подключение

```text
Внутренний ПК ── HTTPS .42:8443 ─────────────┐
                                           ├─ Nginx → Django → PostgreSQL на .42
Внешний ПК ── SSH .42:22 → localhost:8443 ──┘             ├─ FastAPI
                                                         └─ адаптер
                                                              │
                                         SSH к .50 → сырые данные и справочники
```

Данные приложения находятся в отдельном PostgreSQL 17 на ВМ `.42`:
`127.0.0.1:25433`, база **`student`**, схемы **`student_schema`** и
**`adapter_control`**. Системный PostgreSQL на порту `5432` — другой экземпляр.
Поэтому для просмотра БД в pgAdmin нужно подключение к **25433 через SSH**.

Пользователи, служебные таблицы и агрегаты находятся на `.42`. Оригинальная
таблица `paradigm_db.public.electricity_sensor_readings` остаётся на `.50` и
читается под `fdw_reader`. Для справочников используется отдельный читатель.
Туннель к источнику автоматически запускается на ВМ контейнером `source-db`.
Туннель внешнего пользователя работает на его ПК. Это два разных соединения.

Только frontend доступен по сети на порту `8443`. БД, Django, FastAPI и
адаптер нового развёртывания слушают `127.0.0.1` на ВМ.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Внутри сети ответ 403 | IP рабочего ПК входит в разрешённую подсеть в `deploy/vm42/https-allow.conf` |
| Внутри сети соединение не устанавливается | Приложение запущено; сетевой администратор разрешил TCP 8443 от нужной сети к `.42` |
| Внешний `localhost:8443` не открывается | SSH-туннель запущен на вашем ПК; он не завершился ошибкой |
| SSH пишет, что порт занят | Другой туннель уже использует 8443; проверьте существующее подключение |
| Обследование или данные недоступны | На ВМ проверить контейнеры `source-db`, `adapter`, `backend` |
| База не видна в pgAdmin | Подключение направлено к `25433`, а не к системному порту `5432` |

На ВМ посмотреть состояние и последние ошибки:

```sh
cd /home/collective/smart-energy-vm42
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml ps
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml logs --tail=100 frontend backend adapter source-db
```

После изменения разрешённых подсетей применить список без пересборки:

```sh
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml exec -T frontend sh -c 'nginx -t && nginx -s reload'
```

## Развёртывание с нуля и обновление

На уже подготовленной `.42` достаточно команды `start.sh` из раздела 1.
Для новой установки нужны три однократных шага:

1. Скачать проект. Запустить `python deploy/vm42/configure.py` и заполнить
   подключения. Пароли, сертификаты и дампы сохраняются вне Git.
2. Собрать Docker-образы на ПК, передать проект с приватными настройками и
   образы на ВМ, затем загрузить образы через `docker load`.
3. Выполнить `sh deploy/vm42/start.sh` на ВМ. Первое восстановление идёт только
   в пустую новую БД; повторное восстановление поверх данных запрещено.

Точные команды первоначальной подготовки, обновления образов, настройки БД
и остановки — в [технической инструкции](deploy/vm42/README.md).
Для старого локального запуска остаются `docker-compose.yml` и
`docker-compose.adapter.yml`; их не нужно смешивать с Compose-файлами ВМ.

После смены подключения адаптера сохраните новую версию профиля и выполните
предварительный расчёт; только затем активируйте профиль и включите расписание.
При обычной остановке не используйте `down -v`: он удаляет тома БД и ключа Django.
