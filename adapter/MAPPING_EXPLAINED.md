# Подробный разбор `adapter/mapping.py`

Разбор текущего кода на 01.11.2026. Исходный файл: [mapping.py](mapping.py).
Примеры имён и значений ниже учебные: они объясняют формат, а не описывают
фактические показания рабочей БД.

## 1. Для чего нужен этот файл

У источника могут быть свои имена столбцов. Например, время называется
`measured_at`, счётчик — `meter_id`, мощность — `power_kw`.
Остальная часть адаптера работает с фиксированными внутренними именами:
`ts`, `sensor_name`, `pt` и другими.

`mapping.py` связывает эти два представления:

```text
Структура PostgreSQL
    → список реальных столбцов
    → предложения соответствий
    → подтверждённый профиль
    → проверка доступных полей
    → SQL с внутренними именами адаптера
```

В файле два основных пути использования:

```text
Обследование:
inspect_source() → _source_columns() → предложения и примеры для страницы

Пересчёт:
column_types() → source_capabilities() → source_cte()
```

Профиль отдельно проверяет `validate_profile()`. Его сохранением и заданиями
управляет [service.py](service.py). Группировка по часам и вычисление мощности
находятся в [queries.py](queries.py), запись результатов — в [runner.py](runner.py).

## 2. Импорты: какие инструменты используются

| Инструмент | Для чего нужен |
| --- | --- |
| `deepcopy` | Проверять и дополнять копию профиля, сохраняя исходный объект вызывающего кода |
| `Decimal` | Проверять множители и интервал, формировать точные числовые литералы SQL |
| `hashlib`, `json` | Получать отпечаток назначенных столбцов и типов |
| `ZoneInfo` | Проверять имена часовых поясов |
| `psycopg` | Выполнять запросы и обрабатывать конкретные ошибки PostgreSQL |
| `psycopg.sql` | Безопасно собирать SQL с динамическими именами таблиц и столбцов |
| `table_parts` | Разбирать имя `схема.таблица`; функция импортируется из [model.py](model.py) |

## 3. `FIELDS`: какие исходные показатели понимает адаптер

```python
FIELDS = ('ts', 'sensor_name', 'pt', 'p1', 'p2', 'p3', 'qt', 'q1', 'q2', 'q3',
          'st', 's1', 's2', 's3', 'i1', 'i2', 'i3', 'u1', 'u2', 'u3', 'frequency', 't')
```

Это 22 внутренних поля. Они не обязаны совпадать с именами в источнике.

| Поля | Значение |
| --- | --- |
| `ts` | Время показания |
| `sensor_name` | Идентификатор счётчика |
| `pt`, `p1`, `p2`, `p3` | Общая активная мощность и активная мощность трёх фаз |
| `qt`, `q1`, `q2`, `q3` | Общая реактивная мощность и реактивная мощность фаз |
| `st`, `s1`, `s2`, `s3` | Общая полная мощность и полная мощность фаз |
| `i1`, `i2`, `i3` | Токи фаз |
| `u1`, `u2`, `u3` | Напряжения фаз |
| `frequency`, `t` | Частота и температура |

Обязательны только `ts` и `sensor_name`. Для остальных допускается отсутствие
назначения. Дополнительные столбцы источника, не назначенные этим полям,
не включаются в нормализованный набор для расчёта.

## 4. `ALIASES`: откуда берутся предложения названий

Это встроенный словарь синонимов. Например:

```python
'ts': ('ts', 'timestamp', 'measured_at', 'datetime', 'measurement_time', 'время', 'дата'),
'pt': ('pt', 'active_power', 'power_total', 'total_active_power', 'активная_мощность'),
```

Для фазовых показателей словарь дополняется циклом. Например, для `p1`
получаются следующие допустимые имена:

```text
p1
power_l1
active_power_l1
power_phase1
active_power_phase1
```

Предложения строятся по точному совпадению имени без учёта регистра.
Имя `ACTIVE_POWER` подходит для `pt`, а `power_kw` в текущем словаре для `pt`
не предусмотрено — его нужно назначить вручную.

Комментарии столбцов и примеры значений не используются для выбора соответствия.
Из названия также не определяются единицы: `active_power` может содержать Вт
или кВт. Для перевода единиц оператор задаёт множитель.

## 5. Типы и `METRIC_INPUTS`: что можно рассчитать по структуре

Поддерживаемые числовые типы заданы явно:

```python
NUMERIC_TYPES = {'int2', 'int4', 'int8', 'numeric', 'float4', 'float8'}
TIME_TYPES = {'timestamp', 'timestamptz'}
```

Это внутренние имена PostgreSQL: например, `float8` соответствует
`double precision`, `int4` — `integer`.
Текстовый столбец с числами не считается числовым только потому,
что в нескольких примерах встречается строка `"123"`.

`METRIC_INPUTS` описывает зависимости выходных метрик от внутренних полей:

```python
'active_power_w_avg': (('pt',), ('p1', 'p2', 'p3'))
```

Внешний набор означает «ИЛИ», элементы внутри каждой группы — «И»:
для общей активной мощности нужен `pt` **ИЛИ** одновременно `p1`, `p2`, `p3`.

Для напряжения правило другое:

```python
'voltage_avg_v': (('u1',), ('u2',), ('u3',))
```

Здесь достаточно хотя бы одного фазового напряжения. Среднее по доступным
фазам впоследствии вычисляет `queries.py`. Аналогично устроен средний ток.

Этот словарь описывает возможность расчёта **по структуре**. Если столбец
существует, но все его значения NULL, структура подходит, а фактических
измерений всё равно нет. Это выясняется при чтении и проверке данных.

## 6. `validate_profile(value)`: проверка настроек оператора

**Вход:** Python-словарь с настройками источника, обычно полученный из JSON.
**Результат:** проверенная копия словаря с добавленными значениями по умолчанию.
**При ошибке:** исключение вместо сохранения корректного профиля.

Учебный профиль:

```json
{
  "name": "Пример источника",
  "connection": "paradigm",
  "source_table": "public.example_readings",
  "columns": {
    "ts": "measured_at",
    "sensor_name": "meter_id",
    "pt": "power_kw",
    "u1": "voltage_l1",
    "frequency": "frequency_hz"
  },
  "scales": {"pt": 1000},
  "sample_seconds": 5,
  "source_timezone": "Europe/Moscow",
  "timezone": "Europe/Moscow",
  "confirmed": true
}
```

Направление `columns` важно: **ключ — внутреннее поле, значение — имя столбца БД**.
`"pt": "power_kw"` означает «читать `power_kw` как общую активную мощность».

Функция проходит следующие проверки:

| Проверка | Условие текущего кода |
| --- | --- |
| Формат | Профиль должен быть словарём, неизвестные верхнеуровневые настройки запрещены |
| Подтверждение | `confirmed` должен быть именно `True` |
| Имена таблиц | `source_table` и таблица справочника проходят `table_parts()` |
| Часовые пояса | Имена должны распознаваться `ZoneInfo`; выходной пояс допускается только `Europe/Moscow` |
| Сопоставления | Ключи `columns` должны входить в `FIELDS`; назначенное имя — непустая строка без нулевого символа |
| Обязательные поля | Должны быть назначены `ts` и `sensor_name` |
| Множители | Конечные положительные числа, не больше 1 000 000; для времени и ID множители запрещены |
| Интервал | Подтверждённое конечное значение `sample_seconds`: больше 0 и не больше 86 400 секунд |
| Соответствия ID | `sensor_map` связывает строковые ID со строковыми непустыми именами; одинаковые выходные значения запрещены |
| Качество | Допустимы известные настройки с числовыми значениями от 0 до 1 |

Отсутствующие пороги качества добавляются в копию профиля:

| Настройка | По умолчанию | Как используется дальше |
| --- | ---: | --- |
| `min_coverage` | 0.9 | Минимальная доля показаний за сутки |
| `max_duplicate_fraction` | 0.001 | Допустимая доля повторных времён внутри счётчика |
| `interval_tolerance` | 0.2 | Отклонение от подтверждённого интервала |
| `min_interval_match` | 0.9 | Минимальная доля интервалов, попавших в допуск |
| `min_existing_points_ratio` | 0.8 | Защита от существенного уменьшения ранее имевшихся показаний |

Здесь проверяются настройки порогов. Сами проверки покрытия и дубликатов
выполняет `runner.quality_report()`.

`validate_profile()` не подключается к PostgreSQL и не проверяет существование
таблицы или столбцов. Наличие серверного подключения проверяет
`service.build_settings()`, фактическую структуру — следующие функции файла.
Число `5` и `confirmed: true` в профиле также не доказывают реальный интервал:
это подтверждение оператора, которое дополняется проверкой данных.

## 7. `_source_columns(connection, table_name)`: получение настоящих столбцов

**Вход:** открытое соединение PostgreSQL и имя таблицы/представления.
**Результат:** список описаний столбцов в порядке их определения.

Сначала `table_parts()` разбирает имя:

```text
public.example_readings → (public, example_readings)
```

Имена без схемы отклоняются. Поддерживается экранированная запись,
например `"Моя схема"."сырые.показания"`. Схема не угадывается через `search_path`.

Затем выполняется запрос к каталогам PostgreSQL:

| Часть запроса | Назначение |
| --- | --- |
| `pg_class`, `pg_namespace` | Найти объект в заданной схеме |
| `pg_attribute` | Получить имена и номера столбцов |
| `pg_type` | Получить тип; для домена дополнительно читается его непосредственный базовый тип |
| `format_type()` | Получить отображаемое объявление типа, например `numeric(12,3)` |
| `col_description()` | Получить комментарий из БД |
| `NOT a.attnotnull` | Получить признак nullable из атрибута столбца |
| Проверки привилегий | Определить наличие USAGE схемы и SELECT столбца |

Поддерживаются обычные и секционированные таблицы, представления,
материализованные представления и foreign tables. Системные и удалённые
столбцы исключаются; результат сортируется по `attnum`.

Пример одного элемента результата:

```json
{
  "name": "power_kw",
  "type": "float8",
  "declared_type": "double precision",
  "comment": "Активная мощность",
  "nullable": true,
  "readable": true
}
```

`nullable` описывает свойство структуры, а не наличие NULL в прочитанных строках.
Комментарий может быть NULL. Столбец без SELECT может входить в список,
но получит `readable: false` и не будет предложен для назначения.

Если столбцов не найдено, функция выдаёт ошибку. Запрос не читает показания
потребления: он читает метаданные таблицы.

## 8. `inspect_source(connection, table_name)`: обследование для страницы

Функция объединяет структуру, предложения и небольшую выборку значений.

### Шаг 1. Получить структуру

Вызывается `_source_columns()`. Полученный `columns` затем используется
и для предложений, и для построения карточек на странице.

### Шаг 2. Построить предложения

Для каждого поля из `FIELDS` строится список `matches`. В него попадает столбец,
если одновременно выполнены условия:

1. `c['name'].casefold()` точно совпадает с синонимом из `ALIASES[field]`.
2. `readable` равен `True`.
3. Тип подходит назначению: время — временной тип, измерение — числовой.
   Для `sensor_name` ограничение на тип в этом условии не применяется:
   при чтении ID будет приведён к тексту.

Например, `measured_at` типа `timestamptz` — кандидат для `ts`,
а `measured_at` типа `text` — нет. `power_kw` числового типа сам по себе
не станет кандидатом для `pt`: этого имени нет в соответствующем словаре.

Результат для каждого поля формируется так:

```python
suggestions[field] = {
    'column': matches[0] if len(matches) == 1 else None,
    'candidates': matches,
    'needs_confirmation': True,
}
```

| Кандидатов | Результат |
| ---: | --- |
| 0 | `column=None`, список кандидатов пуст |
| 1 | Его имя предложено в `column` |
| Несколько | `column=None`, все имена возвращены в `candidates`; оператор выбирает сам |

Если существуют и `ts`, и `measured_at` подходящего типа, первый из них
не назначается автоматически только из-за порядка столбцов.

### Шаг 3. Определить порядок примеров

При однозначно предложенном столбце времени проверяется наличие подходящего
существующего B-tree индекса: время должно быть первым ключом, индекс —
валидным, готовым и без частичного условия.

Если такой индекс найден, запрос примеров дополняется `ORDER BY время DESC`.
Иначе дополнительной сортировки нет. Поэтому примеры не всегда являются
последними показаниями таблицы. Индекс функция не создаёт.

### Шаг 4. Прочитать до пяти строк

В SELECT включаются только столбцы с `readable: true`. Запрос собирается через
`sql.Identifier`, например:

```sql
SELECT "measured_at", "meter_id", "power_kw"
FROM "public"."example_readings"
ORDER BY "measured_at" DESC
LIMIT 5
```

Чтение выполняется внутри `connection.transaction()`. Если уже есть внешняя
транзакция, это позволяет изолировать запрос savepoint и сохранить её пригодной
для работы после ошибки примера.

Обрабатываются две конкретные ошибки: отмена запроса, включая тайм-аут,
и недостаточные привилегии. Вместо потери структуры возвращается предупреждение
и пустой `sample`. При отсутствии читаемых столбцов запрос примеров не выполняется.
Другие ошибки PostgreSQL здесь не превращаются автоматически в успешное обследование.

### Шаг 5. Вернуть результат

| Поле ответа | Содержимое |
| --- | --- |
| `columns` | Настоящая структура |
| `suggestions` | Предложения по внутренним полям |
| `sample` | До пяти примеров строк |
| `warnings` | Предупреждения обследования |
| `notice` | Напоминание подтвердить единицы и смысл назначений |

`process_job()` сохраняет этот результат событием `inspection` в задании.
Страница получает событие при опросе API и отображает карточки.
Применение предложений выполняется отдельно на фронтенде и заполняет только
ещё не назначенные поля. Сам `inspect_source()` профиль не активирует.

## 9. `column_types(connection, profile)`: доступные типы перед расчётом

Хотя эта функция расположена последней в файле, в цепочке пересчёта
она вызывается перед проверкой возможностей источника.

```python
return {
    c['name']: c['type']
    for c in _source_columns(connection, profile['source_table'])
    if c['readable']
}
```

Из полного описания получается компактный словарь только читаемых столбцов:

```json
{
  "measured_at": "timestamptz",
  "meter_id": "text",
  "power_kw": "float8",
  "voltage_l1": "numeric",
  "frequency_hz": "float8"
}
```

Отсутствующий и недоступный для SELECT столбцы в этом словаре отсутствуют.
Поэтому последующая проверка описывает обе ситуации как «отсутствует или недоступен».
Получение структуры здесь повторяется: старое обследование страницы не заменяет
проверку состояния БД перед выполнением задания.

## 10. `source_capabilities(profile, types)`: что доступно этому профилю

**Вход:** назначения профиля и словарь фактических читаемых типов.
**Результат:** доступные поля/метрики, предупреждения и отпечаток структуры.

Сначала проверяются обязательные поля. Для `ts` и `sensor_name` должны быть
назначены существующие читаемые столбцы. Тип времени должен входить в `TIME_TYPES`.
Отсутствующее время не заменяется текущей датой, отсутствующий ID не генерируется.

Затем проверяются типы назначенных измерений. Если столбец существует и читается,
но имеет неподходящий тип, возникает ошибка. Это отличается от отсутствующего
необязательного столбца, для которого разрешён NULL.

После этого строится `available_fields`: внутренние поля, назначения которых
присутствуют в `types`. По `METRIC_INPUTS` определяется возможность расчёта метрик:

```python
any(all(field in fields for field in group) for group in alternatives)
```

`all()` проверяет наличие всех полей одного варианта, `any()` — наличие хотя бы
одного подходящего варианта. Так реализуется правило «`pt` или три фазы».

`missing_columns` содержит назначения, у которых было задано имя, но оно
не найдено среди читаемых столбцов. Поле, которое оператор вообще не назначил,
в этот список не добавляется; зависимая метрика всё равно может быть недоступна.

Предупреждения объясняют исчезнувшие назначения и отсутствие общей мощности.
При отсутствии мощности структурно допустим расчёт остальных показателей
и количества записей; достаточность самих записей проверяется дальше.

### Для чего нужен `signature`

Для каждого внутреннего поля собирается пара:

```text
внутреннее поле → [назначенное имя столбца, его доступный тип]
```

Эти данные сериализуются в JSON и хешируются SHA-256. Получается отпечаток
назначений и типов на момент проверки. При ручной записи `runner.refresh()`
сравнивает его с отпечатком успешного preview.

Это не хеш всей таблицы. Он не описывает содержимое строк, комментарии или
посторонние неназначенные столбцы. Изменения профиля и подключений дополнительно
контролируются отдельным `runner.fingerprint()`.

## 11. `source_cte(profile, column_types)`: формирование SQL чтения

Функция получает профиль и проверенные типы, повторно вызывает
`source_capabilities()`, затем собирает SELECT для внутреннего формата адаптера.
Она возвращает объект SQL, а не выполняет расчёт сама.

### Время

Для `timestamptz` используется исходный момент времени.
Для `timestamp` без зоны применяется `source_timezone` профиля:

```sql
"measured_at" AT TIME ZONE 'Europe/Moscow'
```

Например, локальные `12:00` Москвы интерпретируются как `09:00 UTC`.
Границы периода также переводятся в локальную шкалу исходного `timestamp`,
чтобы фильтрация выбирала соответствующие строки.

### Идентификатор счётчика

Назначенный столбец приводится к тексту:

```sql
"meter_id"::text AS "sensor_name"
```

NULL при таком преобразовании остаётся NULL. Проверка пустого/NULL ID
в выбранном периоде находится в `runner.validate_required_rows()`.

### Измерения и множители

Если назначенный столбец есть в `column_types`, значение приводится к `numeric`
и умножается на подтверждённый коэффициент. Если множитель не задан, используется 1.

```sql
"power_kw"::numeric * 1000 AS "pt"
```

В учебном примере значение 1.5 кВт становится 1500 Вт. Само решение о единицах
берётся из профиля, а не выводится из имени `power_kw`.

Для `float4` и `float8` предварительно проверяются NaN и бесконечности:

```sql
CASE
    WHEN "power_kw"::text IN ('NaN', 'Infinity', '-Infinity') THEN NULL
    ELSE "power_kw"::numeric * 1000
END AS "pt"
```

Эта проверка нужна до преобразования: PostgreSQL 13 не может привести float
Infinity к numeric. Неконечные значения числовых полей дополнительно очищаются
далее в `queries.py`.

### Неназначенные, отсутствующие и недоступные измерения

Для них формируется:

```sql
NULL::numeric AS "p1"
```

Запрос не обращается к несуществующему столбцу. Ноль здесь не подставляется.
Это позволяет сохранить доступные независимые измерения.

### Границы и безопасность SQL

Условие периода имеет смысл `[start, end)`: начало включается, конец исключается.
Для исходного `timestamptz` сокращённая проекция выглядит так:

```sql
SELECT
    "measured_at" AS "ts",
    "meter_id"::text AS "sensor_name",
    "power_kw"::numeric * 1000 AS "pt",
    NULL::numeric AS "p1"
FROM "public"."example_readings"
WHERE "measured_at" >= %(start)s
  AND "measured_at" < %(end)s
```

Здесь показаны только четыре из 22 выходных полей и опущена защита float
для краткости. Реальный запрос содержит все `FIELDS`.

Имена формируются через `sql.Identifier`, числовые множители и часовой пояс —
через типизированные `sql.Literal`, границы — через параметры запроса.
Текст назначения используется как имя столбца, а не как произвольная SQL-формула.

## 12. Как всё связывается на одном примере

Для учебного профиля выше порядок следующий:

1. Обследование обнаруживает реальные `measured_at`, `meter_id`, `power_kw`,
   `voltage_l1`, `frequency_hz`.
2. По словарю предлагаются время, ID, напряжение L1 и частота. Для `power_kw`
   оператор вручную назначает `pt` и множитель 1000.
3. Оператор подтверждает настройки; `validate_profile()` проверяет документ.
4. Перед preview `column_types()` заново читает реальные доступные типы.
5. `source_capabilities()` подтверждает структурную доступность общей мощности,
   напряжения и частоты; остальные показатели помечаются недоступными.
6. `source_cte()` формирует чтение: значения переименовываются, мощность
   переводится в Вт, остальные поля заполняются NULL.
7. `queries.py` и `model.py` рассчитывают агрегаты; `runner.py` проверяет качество
   и при разрешённой записи заменяет данные назначения.

Если перед новым preview удалить `frequency_hz`, частота станет NULL
с предупреждением, а мощность и напряжение останутся доступны.
Если удалить `measured_at`, расчёт остановится. Если столбец изменится
между preview и ручной записью так, что изменится отпечаток назначений/типов,
потребуется новый preview.

## 13. Границы ответственности

| Вопрос | Где решается |
| --- | --- |
| Как получить названия, типы и предложения? | `mapping.py` |
| Как показать карточки и применить предложение? | [ColumnMappingEditor.jsx](../Фронт/smart_energy/src/pages/aggregation/ColumnMappingEditor.jsx) и [AggregationPage.jsx](../Фронт/smart_energy/src/pages/aggregation/AggregationPage.jsx) |
| Как проверить реальное покрытие, дубликаты и обязательные значения? | `runner.py` |
| Как сложить фазы, получить часовые суммы и количества? | `queries.py` |
| Как вычислить средние и энергию из этих сумм? | `model.py` |
| Как сохранить профиль, поставить задание и включить расписание? | `service.py`, `store.py` |

Наличие времени и ID в профиле не гарантирует успешную агрегацию: нужны
существующие строки и прохождение проверок качества. Пустой источник не
заполняется нулями. Наличие столбца также не гарантирует наличие корректных
значений в нём. Эти различия проверяются после этапа сопоставления.
