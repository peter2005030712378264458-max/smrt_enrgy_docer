# Адаптер агрегаций

Адаптер читает PostgreSQL заказчика, приводит поля к формату приложения и заменяет часовые/суточные агрегаты в `student`. Источник доступен только для чтения. Справочники и исходные таблицы не изменяются. Явная команда `upgrade-aggregates` добавляет счётчики корректных значений в существующие таблицы назначения; сами таблицы не создаёт. Результаты проверки кода и сценариев с неполной структурой описаны в [REVIEW.md](REVIEW.md).

## Возможности и границы

Подробный разбор получения структуры, предложений соответствий, проверки
профиля и формирования SQL: [MAPPING_EXPLAINED.md](MAPPING_EXPLAINED.md).

- Ручной пересчёт и автоматический запуск в 00:00 `Europe/Moscow`.
- В обычном автоматическом запуске обрабатывается вчерашний день; после простоя — пропущенные завершённые дни.
- При первом включении расписания обрабатывается вчерашний день. Историческую загрузку запускает оператор.
- Повтор вчерашнего дня по умолчанию в 00:15 учитывает запоздавшие показания; можно отключить или изменить время.
- Сегодняшние и будущие дни исключаются. `--from` включается, `--to` не включается.
- Каждые сутки заменяются одной транзакцией сразу в обеих таблицах. Уже завершённые дни сохраняются при ошибке следующего дня.
- Пустой источник, недостаточное покрытие, дубликаты, исчезнувшие счётчики и несовместимая структура блокируют запись. Предварительный расчёт показывает причины.
- Профили неизменяемые: редактирование создаёт новую версию. Активация требует успешного предварительного расчёта.
- Профиль связан с отпечатком подключений и параметров расчёта без паролей. При смене источника или назначения обработка старой версии блокируется; требуется новая проверенная версия.
- На один комплект таблиц назначения поддерживается один активный профиль. Параллельное объединение независимых источников разных заказчиков в те же сутки не поддерживается: замена дня затрагивает все его строки.
- Поддерживаются числовые измерения мощности, тока, напряжения, частоты и температуры. Без мощности остальные показатели также агрегируются; энергия остаётся неизвестной. Накопленная энергия и произвольные SQL-выражения профиля не поддерживаются.
- Имена таблиц и представлений задаются как `schema.table`; для нестандартных имён допустима запись `"Моя схема"."сырые.показания"`. Имена столбцов могут быть кириллическими. Идентификаторы экранируются, значения передаются параметрами.
- Выходной часовой пояс — Москва, совместимо с текущим дашбордом. Для исходного `timestamp` без зоны явно задаётся `source_timezone`; `timestamptz` уже содержит момент времени.

## Установка в Docker

Все команды выполняются из корня проекта. PostgreSQL остаётся внешним; существующий SSH-туннель должен работать. В контейнере адрес туннеля — `host.docker.internal:15432`, а не `127.0.0.1`.

1. Скопировать `adapter/.env.example` в `adapter/.env`. Задать реальные подключения и случайный внутренний `ENERGY_ADAPTER_TOKEN` длиной не менее 24 символов. Источник требует `CONNECT`, `USAGE` схем и `SELECT`; назначение — `SELECT`, `INSERT`, `DELETE` на двух таблицах. Для установки служебной схемы нужны права создания схемы/таблиц; при необходимости использовать отдельный `ENERGY_ADAPTER_CONTROL_DSN`.
2. В корневом `.env` задать тот же `ENERGY_ADAPTER_TOKEN`. До проверки истории оставить `ENERGY_USE_STORED_ENERGY=0`.
3. Собрать образ и явно установить служебные таблицы:

   ```powershell
   docker compose -f docker-compose.yml -f docker-compose.adapter.yml build adapter
   docker compose -f docker-compose.yml -f docker-compose.adapter.yml run --rm --no-deps adapter init-control
   docker compose -f docker-compose.yml -f docker-compose.adapter.yml run --rm --no-deps adapter upgrade-aggregates
   ```

4. Запустить сервисы с дополнением конфигурации:

   ```powershell
   docker compose -f docker-compose.yml -f docker-compose.adapter.yml up -d --build
   ```

Основной `docker-compose.yml` не изменён. Дополнение задаёт адрес адаптера для Django; порт адаптера наружу не публикуется. Доступ к API защищён внутренним токеном. TLS для браузера обеспечивает существующий Nginx.

Состояние, профили и задания хранятся в `adapter_control` внешней PostgreSQL, поэтому отдельный Docker volume для checkpoint не требуется. Пересоздание контейнера их не удаляет. Добавьте служебную схему в резервное копирование БД.

## Работа через приложение

Управление доступно пользователю Django с `is_staff=True`. Обычный пользователь не получает доступ к операциям и профилям. Роль назначается существующим администратором Django.

Открыть **«Источники и агрегации»** в меню или `/aggregation`.

1. Выбрать серверное подключение и таблицу, запустить обследование.
2. Применить предложения и проверить каждое соответствие. Название столбца не доказывает единицу измерения: множитель `1000` переводит кВт в Вт, `1` оставляет Вт.
3. Подтвердить часовой пояс, интервал и единицы. Сохранить новую версию.
4. На вкладке «Пересчёт» выбрать завершённый день и выполнить предварительный расчёт без записи.
5. Проверить количество строк, интервалы, долю покрытия и ошибки. При успехе активировать версию на вкладке источника.
6. Сохранить копию существующих агрегатов до первой записи. Отдельно подтвердить замену и нажать «Записать агрегаты».
7. Во вкладке расписания включить ежедневную обработку. **По умолчанию она выключена.** При включении после полуночи вчерашний день может быть обработан сразу.

Задания выполняются в фоне, закрытие браузера их не отменяет. История показывает период, профиль, попытки, события и ошибку. При неуспехе ручного задания исправьте причину и создайте новую проверку/задание. Автоматические задания повторяются до пяти попыток через пять минут при ошибке БД или качества; после исчерпания попыток исправленный источник будет подхвачен следующим ежедневным заданием. При необходимости восстановить день раньше — запустить ручной пересчёт; автоматический прогресс от этого не изменится.

Внутренний планировщик имеет единственного активного исполнителя через advisory lock PostgreSQL. Автоматическая и ручная запись дополнительно используют блокировки таблиц назначения на уровне адаптера. Внешние SQL-скрипты эти блокировки не соблюдают: не запускайте старый пересчёт параллельно.

## Подключение заказчика

DSN хранятся только в окружении сервера. Дополнительные подключения задаются JSON-объектом в `ENERGY_ADAPTER_CONNECTIONS`, например:

```text
ENERGY_ADAPTER_CONNECTIONS={"customer":"host=host.docker.internal port=15432 dbname=customer user=reader password=replace-me"}
```

При наличии `ENERGY_AGG_SOURCE_DSN` автоматически доступен псевдоним `paradigm`. Браузер получает только псевдонимы, структуру и небольшую выборку данных; оператору нужен доступ к этим сведениям. Для сложных паролей соблюдайте синтаксис DSN libpq.

### Отдельное подключение к справочнику

Если роль сырых показаний (например, `fdw_reader`) не имеет права читать `public.sensor_directory`, задайте в `adapter/.env` переменную `ENERGY_AGG_DIRECTORY_DSN`. Она должна указывать на базу со справочником под уже имеющей доступ ролью, например `student`. Учётные данные передаются только через окружение сервиса. Это не меняет подключение к сырым показаниям, назначение агрегатов или настройки Django.

Появится служебный псевдоним `directory`. Он используется для проверки справочника и не предлагается в списке источников сырых показаний; обследование произвольных таблиц через него запрещено. При выборе справочника действует порядок:

1. Явный `directory_connection` из сохранённого профиля.
2. Отдельное подключение `directory`, если оно настроено.
3. Подключение источника, если отдельного подключения нет.

Существующие версии без явного `directory_connection` начинают использовать настроенный отдельный справочник без пересоздания версии и изменения автоматического прогресса. Если в версии явно стоит `directory_connection: "paradigm"`, эта настройка сохраняет приоритет: для смены создайте версию с `directory_connection: "directory"` или без этого поля. Добавление отдельного reader не изменяет отпечаток исходных показаний и назначения.

Подключение справочника выполняет SELECT в read-only сессии. Права ролей PostgreSQL менять не требуется, если выбранная роль уже имеет нужное чтение. После изменения окружения пересоздайте только адаптер:

```powershell
docker compose -f docker-compose.yml -f docker-compose.adapter.yml up -d --build --no-deps adapter
```

Профиль текущего источника: `adapter/profiles/paradigm.json`. Пример для другого источника:

```json
{
  "name": "Заказчик: мощность в кВт",
  "connection": "customer",
  "source_table": "public.measurements",
  "columns": {"ts": "measured_at", "sensor_name": "meter_id", "pt": "active_power"},
  "scales": {"pt": 1000},
  "source_timezone": "Europe/Moscow",
  "timezone": "Europe/Moscow",
  "sample_seconds": 5,
  "sensor_map": {"42": "F1 Smart Meter"},
  "directory_connection": "paradigm",
  "directory_table": "public.sensor_directory",
  "directory_column": "sensor_name",
  "confirmed": true
}
```

`sensor_map` преобразует исходные ID в имена уже существующего справочника приложения. Пустая карта означает сохранение исходных имён. Все фактически обрабатываемые имена проверяются по справочнику. Привязки к зданиям и помещениям не создаются.

Дополнительный JSON задаёт `sensor_map` и справочник профиля. Все счётчики справочника входят в ожидаемый состав, даже без показаний за выбранный диапазон. Пустой или некорректный справочник запрещает замену данных.

Алгоритм версии 3 исключает точные повторы, усредняет разные значения одного времени и сворачивает статистики в окна `window_seconds=10`. Подтверждённый `sample_seconds` остаётся фактическим интервалом источника. Фазы складываются только внутри одного исходного показания, средние объединяются с собственными counts.

Пропуски, дубликаты, низкая полнота и отсутствие мощности у всех счётчиков не блокируют доступные метрики. Старые пороги `min_coverage`, `max_duplicate_fraction`, `min_interval_match`, `min_existing_points_ratio` принимаются для совместимости, но больше не являются условиями допуска дня.

Каждому ожидаемому счётчику создаются 24 часовые и одна суточная строка. Отсутствующие показатели — NULL, counts без показаний — 0. Успешно прочитанный пустой день заменяет прежние значения NULL-строками; технический сбой не считается пустым источником.

`available_energy_kwh` сохраняет энергию известных измерений без двойного учёта времени. Длительность ограничена подтверждённым интервалом, следующим показанием и границей расчёта. `energy_kwh` хранит полный итог только при известной мощности за всё время часа и все 24 часа суток. Пропуски не заполняются нулём или средним. Доступная энергия складывается по известным вкладам; без вкладов остаётся NULL, измеренный ноль сохраняется.

Перед новой версией явно выполнить `upgrade-aggregates` и `upgrade-control` с остановленным старым writer. Новые поля legacy-строк остаются NULL. Нужны новая версия профиля и свежий preview. Control-схема версии 2 не устанавливается автоматически при `serve`.

Локальная ошибка дня создаёт `day_skipped`, следующие даты продолжаются. `day_results` хранит результаты независимо от усечения журнала. `attempted_until` означает рассмотренные даты, `processed_until` — непрерывную успешную запись. Старые пропуски доступны ручному пересчёту; массовая история автоматически не восстанавливается.

Самостоятельное обновление ВМ: [инструкция и откат](../deploy/vm42/AGGREGATION_UPDATE.md).

### Отсутствующие столбцы и значения

Обязательны только время и идентификатор счётчика. Отсутствие назначенного столбца времени/ID, неверный тип времени, NULL времени либо пустой/NULL ID останавливают расчёт с понятной ошибкой до замены агрегатов. Время не подставляется из текущей даты. NULL времени проверяется во всём источнике: такую строку нельзя отнести к выбранному периоду. На большом источнике эта проверка может потребовать индекс или подготовленное администратором представление; адаптер не выполняет DDL в источнике.

Остальные столбцы необязательны. Если назначенный столбец удалён или недоступен по SELECT, для него используется `NULL`, в журнале появляется предупреждение, а доступные показатели продолжают рассчитываться. Если существующий назначенный столбец имеет нечисловой тип, профиль нужно исправить: текст не преобразуется в измерение автоматически. `NULL`, `NaN` и бесконечные измерения не считаются нулевыми.

Общая активная, реактивная и полная мощности вычисляются из своего общего значения либо из **всех трёх** корректных фаз одного показания. Частичные фазы сохраняются отдельно; они не складываются между конфликтующими строками. Ток и напряжение используют доступные фазы. Полная энергия неизвестна при пропусках мощности или времени; доступная энергия сохраняется отдельно. Пороги покрытия не блокируют запись.

Событие `schema` содержит доступность по структуре, `missing_columns` и отпечаток назначенных столбцов/типов. Событие `quality` показывает доступные фактически за день показатели и основание покрытия (`active_power` или `readings`). После изменения структуры между preview и ручной записью требуется новый preview; старые preview без отпечатка также нужно повторить. Постановка нового preview сбрасывает отметку проверки профиля, не меняя сохранённые агрегаты.

Обследование читает реальные имена, типы, комментарии и права столбцов из каталога PostgreSQL. До пяти строк служат только примером. NULL в примере не скрывает существующий столбец. При тайм-ауте примера структура остаётся доступной с предупреждением. Предложения учитывают типы и SELECT, но смысл, единицы и интервал всегда подтверждает оператор. Ручные соответствия при применении предложений сохраняются.

### Счётчики корректных измерений

Часовые агрегаты хранят `<metric>_count` для каждого поля `METRICS`, суточные — для полей `DAILY_METRICS`. Это количество корректных нормализованных моментов измерений конкретного показателя, а `points_count` считает все уникальные моменты, включая NULL-метрики. Исходные повторы учитываются только в диагностике. Средние в API используют counts своих метрик. Мощность за неделю сначала усредняется по времени каждого счётчика, затем складывается между счётчиками. Группировка сохраняет московский календарь.

CLI checkpoint имеет версию 2 и хранит границу рассмотрения и пропущенные даты. Старый checkpoint не переинтерпретируется автоматически. Для явного первого запуска с новым файлом используйте `--from ... --to ... --apply --initialize-checkpoint --checkpoint новый_файл`; повтор существующих дат без этого флага не меняет автоматический прогресс. Новый checkpoint создаётся только после завершённого расчёта, существующий не перезаписывается этим флагом.

Полный ожидаемый состав для CLI задаётся через `--profile` и его справочник, как в HTTP-сервисе. Низкоуровневый режим без профиля не знает полного списка устройств и создаёт строки только для обнаруженных счётчиков. Время и ID остаются обязательными в обоих режимах; NULL мощности допустим.

Перед первым запуском новой версии остановите старый адаптер и выполните `python -m adapter upgrade-aggregates` в его серверном окружении. Команда изменяет только две таблицы назначения одной транзакцией, соблюдает блокировку пересчёта и повторно безопасна. Старые строки получают NULL счётчиков: угадывать их через `points_count` нельзя. Точные средние таких строк недоступны до проверенного пересчёта из сырых показаний. Формат отпечатка профиля обновлён; для существующего подключения создайте новую версию профиля и выполните preview перед активацией.

Перед пересчётом истории сохраните резервную копию БД. Не отключайте проверки качества ради перезаписи старых данных: дни без достаточного источника требуют отдельного решения оператора. На ВМ `deploy/vm42/start.sh` выполняет остановку предыдущего адаптера и этот аддитивный upgrade перед запуском сервисов; автоматического пересчёта истории и переключения энергии команда запуска не выполняет.

## Ручной запуск без интерфейса

Прежний синтаксис сохранён:

```powershell
python -m adapter --from 2026-10-15 --to 2026-10-16 --sample-seconds 5
python -m adapter --from 2026-10-15 --to 2026-10-16 --sample-seconds 5 --apply
```

Без `--apply` записи нет. `.env` при локальном запуске автоматически не загружается: задайте переменные в PowerShell. Явный диапазон не читает и не изменяет старый файловый checkpoint. Пустой источник не продвигает автоматический прогресс. `--allow-empty` в прежнем режиме позволяет очистить день; сервис через UI такой обход не предоставляет.

Проверка с профилем и нормализацией:

```powershell
python -m adapter --profile adapter/profiles/paradigm.json --from 2026-10-15 --to 2026-10-16
```

В Docker для разового задания используйте `run --rm --no-deps adapter` с теми же аргументами вместо `python -m adapter`. Изменить параметры энергии утверждённого профиля флагами нельзя: сохраните новую версию профиля. Режим без профиля сохранён для совместимости и не выполняет полный набор проверок качества сервиса.

## Переход приложения на сохранённую энергию

Для равномерных показаний мощности в Вт адаптер оценивает энергию как `SUM(power) × sample_seconds / 3600000`. Интервал 5 секунд подтверждён для текущего источника. Это оценка по полученным точкам, без восстановления неизвестного потребления в длинных пропусках. Для других заказчиков интервал подтверждается отдельно.

Старые агрегаты могли быть заполнены SQL с формулой для минутного интервала. Поэтому переключение выполняется отдельно:

1. Сохранить согласованную копию обеих таблиц (например, одним `pg_dump` только этих таблиц) и служебного состояния.
2. Пересчитать доступную приложению историю проверенным профилем. Периоды без сырых данных считать непроверенными; не обещать для них корректную энергию.
3. Проверить независимым SQL суммы и контрольные дни.
4. В корневом `.env` установить `ENERGY_USE_STORED_ENERGY=1` и пересоздать Django и аналитический сервис с дополнительным Compose-файлом.

Оба сервиса должны получить одинаковое значение флага. При запуске вне Compose задайте его в окружении каждого процесса. По умолчанию действует прежняя формула, чтобы новая версия не включала непроверенные значения автоматически.

При включённом флаге сводка, графики, рейтинг, тепловая карта, помещения и энергия сравниваемых периодов используют сохранённое `energy_kwh`. Средняя мощность и Z-тест остаются прежними. Если у любой участвующей строки энергия `NULL`, итог также `NULL`, интерфейс показывает отсутствие значения, а не нулевое потребление. Пустые временные интервалы графика не дополняются нулевой энергией.

## Тестирование

Изолированное окружение содержит только вымышленные данные и временный PostgreSQL 13. Рабочие DSN и `.env` в образ не копируются.

```powershell
docker compose -p smart-energy-adapter-tests -f adapter/tests/compose.yml run --build --rm tests
```

Запускаются unit/integration-тесты адаптера, Django, аналитики и реальные SQL-запросы потребителей. В source/target создаются только базы с именами `test_adapter_source`, `test_adapter_target` на тестовом сервере.

Дополнительная HTTP-проверка gateway → API → worker → PostgreSQL:

```powershell
docker compose -p smart-energy-adapter-tests -f adapter/tests/compose.yml --profile ui up -d ui
docker compose -p smart-energy-adapter-tests -f adapter/tests/compose.yml exec -T ui python -m adapter.tests.http_smoke
```

Тестовый Django доступен только на `127.0.0.1:15000`. Для ручной UI-проверки запустить Vite с `VITE_API_PROXY_TARGET=http://127.0.0.1:15000`, отдельным портом и войти как `operator@example.test` / `AdapterTest123!`. Это одноразовая учётная запись только в тестовой БД. Не запускайте основной набор тестов одновременно с UI-фикстурой: они намеренно сбрасывают одни и те же тестовые таблицы.

Остановить тестовое окружение:

```powershell
docker compose -p smart-energy-adapter-tests -f adapter/tests/compose.yml --profile ui down
```

Frontend: `npm run lint`, `npm run build`. После сборки обновить `frontend-dist.tar.gz` из содержимого `dist/`: действующий Dockerfile фронтенда отдаёт архив, а не собирает `src`.

## Откат

1. Выключить расписание и остановить только контейнер адаптера. Остановка не отменяет уже завершённые дни.
2. При необходимости вернуть `ENERGY_USE_STORED_ENERGY=0` одновременно для Django и аналитического сервиса и пересоздать их.
3. Вернуть предыдущие версии кода и frontend-архива.
4. Если требуется восстановить прежние значения — загрузить сохранённые строки в промежуточные таблицы и восстановить только затронутые дни одной транзакцией для обеих витрин. Простое возвращение кода данные не восстанавливает.
5. Восстановить согласованное служебное состояние. При смене профиля прогресс новой версии начинает отсчёт отдельно; не удаляйте контрольные таблицы вслепую.

`adapter_control` не удаляется автоматически. Для остановки адаптера основной дашборд останавливать не нужно. Старый SQL сохранён, но его минутная формула энергии не является эталоном для показаний с интервалом 5 секунд.

### Сопоставление столбцов в интерфейсе

После обследования таблицы раздел «Источник и соответствия» показывает карточки её столбцов с типами и примерами значений. Перетащите карточку на показатель или выберите её кликом (Enter/Space с клавиатуры), затем нажмите «Назначить» у показателя. Поиск фильтрует карточки по названию, типу и описанию.

Существующее соответствие можно заменить, убрать или ввести вручную. Любое изменение соответствий и множителей сбрасывает подтверждение профиля; для сохранения новой версии подтвердите настройки повторно. Карточки изменяют тот же `profile.columns`; API и формат JSONB не меняются. До завершения обследования ручной ввод доступен, карточки ещё не отображаются.

После обследования таблицы режим «По данным источника» скрывает необязательные показатели без найденного или назначенного столбца. «Показать остальные» раскрывает полный список для ручных сопоставлений с нестандартными именами. Время и ID датчика всегда видимы и обязательны. Назначенные, но удалённые из источника столбцы остаются видимыми с предупреждением. Отдельно показано, какие показатели можно рассчитать по структуре и какие останутся NULL. Фильтр не удаляет сохранённые сопоставления и не использует примеры значений: `NULL` у одного датчика не означает отсутствие столбца для всех.
