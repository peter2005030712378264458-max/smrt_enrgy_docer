# Проверка процесса агрегации

## Отсутствующая мощность отдельных счётчиков — 18 октября 2026

Счётчики без единого корректного значения активной мощности теперь дают предупреждение и сохраняют `NULL` мощности/энергии, не блокируя остальные устройства. Доступные другие показатели сохраняются. Полное потребление всех устройств при таком пропуске неизвестно. Нулевые измерения остаются корректными; частично потерянная мощность ниже порога покрытия, полностью отсутствующая мощность всех устройств, пустой источник и остальные ошибки качества продолжают блокировать запись.

Пройдены 28 тестов адаптера, 33 Django-теста, 14 тестов аналитики и SQL-проверки потребителей. Шесть новых интеграционных сценариев проверяют смешанный день с отсутствующей мощностью, доступное напряжение, повторную запись без дубликатов, настоящий ноль, запрет записи при отсутствии мощности у всех устройств, частичные пропуски, NaN и полный путь preview → apply с предупреждением. Итог с неизвестной энергией проверен как `NULL`. Frontend прошёл lint/build; предупреждения видны перед записью и в истории, архив сборки обновлён.

В работающем окружении обновлены только контейнеры adapter/frontend. Расписание было и осталось выключенным. Новая проверка `61a08d9d-0643-4369-b541-2308793d58d0` за 17.10.2026 прошла с предупреждением о К268.27 и К268.n237. После неё задание записи `e2dc0e73-e91d-4da7-98b2-eec49211d116` успешно записало 1176 часовых и 49 суточных строк из 826678 показаний. В PostgreSQL проверены 1128 часовых и 47 суточных значений энергии; остальные 48 часовых и 2 суточных значения — `NULL`. Суммы известной энергии совпали: около 670.5141944444445 кВт·ч. Полный итог, учитывающий неизвестные значения, — `NULL`.

Перед записью сохранена точная JSON-копия прежних строк обеих таблиц выбранного дня в игнорируемом `.venv/adapter-backups/2026-10-17-before-null-policy.json` (SHA256 `B95BA2C54336A980E8BBA9CEBC8D247365607AA80E0B4245303FA74F0429A778`). В обеих таблицах этот день ранее был пуст. Для отката именно этой записи достаточно в одной транзакции под блокировкой адаптера удалить строки 17.10 по московским границам из обеих таблиц; другие дни не затрагивать. Ручной запуск автоматический прогресс не изменял. Откат кода возвращает блокировку проверки при нулевом покрытии, но сам по себе не отменяет записанные данные.

## Отдельное чтение справочника — 18 октября 2026

Добавлено необязательное `ENERGY_AGG_DIRECTORY_DSN`: исходные показания и справочник могут читаться под разными ролями. Приоритет явного `directory_connection` сохранён; без новой настройки работает прежний выбор подключения. Профили без явно выбранного справочника сохраняют совместимость своих отпечатков и прогресса. Служебный псевдоним `directory` не доступен для обследования произвольных таблиц через интерфейс.

Пройдены 22 теста адаптера, 33 Django-теста, 14 тестов аналитики и реальные SQL-проверки потребителей. Новый интеграционный тест воспроизводит отказ роли сырых данных на справочнике и успешные preview/apply через отдельную роль с ограниченными правами. Обратный доступ роли справочника к сырым данным также запрещён. Frontend прошёл lint/build; архив обновлён.

В текущем окружении с разрешения владельца настроено отдельное чтение справочника под уже используемой Django ролью `student`. Сырые данные продолжают читаться под `fdw_reader`. Настройки Django, роли PostgreSQL и таблицы агрегатов не изменялись. Учётные данные сохранены только в игнорируемом `adapter/.env`.

Предварительный расчёт 14.10.2026 получил 181 имя из справочника и рассчитал 1176 часовых/49 суточных строк из 821790 исходных показаний без записи. Ошибка прав устранена. Проверка качества выявила два счётчика с 185 и 176 строками без корректной активной мощности, поэтому задание корректно завершилось ошибкой качества. Пороги и исходные значения не изменялись. Результат доступен в новой записи истории проверки. Backend и аналитический контейнер при применении изменения не пересоздавались; маршрут дашборда после обновления frontend возвращает HTTP 200.

## Адаптер-сервис и интерфейс — 18 октября 2026

Реализованы профили источников, обследование схемы, явная нормализация единиц и имён, очередь заданий, расписание, внутренний HTTP API, Django gateway с проверкой `is_staff`, раздел `/aggregation` и переключение потребителей на сохранённую энергию. Рабочие БД и их расписания при разработке не изменялись.

Проверки выполнены в отдельном Docker Compose-проекте `smart-energy-adapter-tests` с PostgreSQL 13, Python 3.12 и вымышленными данными. Исходные данные и агрегаты находятся в разных тестовых базах. Рабочие `.env` не включаются в образы.

- 19 unit/integration-тестов адаптера: соответствия, единицы, даты, расписание, запись, повторный запуск, транзакционный откат двух витрин, пустой/неполный источник, дубликаты, блокировки, source read-only, остановка на границе суток, NULL энергии, сбой контрольного состояния после commit и восстановление, запрет пропуска необработанных дней при повторе.
- 23 Django-теста: существующие consumption-сценарии, права на управление адаптером, ограничение маршрутов proxy, недоступность сервиса, SQL сохранённой энергии и переключатель отката.
- 14 pytest-тестов аналитики, включая сохранение NULL энергии и независимость расчёта мощности от выбора источника энергии.
- Реальные SQL-запросы Django и аналитики против тестовых агрегатов: сводка, часовой/суточный график, рейтинг, помещения, тепловая карта, статистика периода и распространение NULL.
- HTTP-проверка JWT → Django → private API → worker → PostgreSQL: отказ без авторизации/внутреннего токена, обследование, preview, apply, активация и проверка записанной энергии.
- `npm run lint`, `npm run build`, обновление и проверка содержимого `frontend-dist.tar.gz`.
- Сборка отдельного production-образа адаптера; секреты и тестовый код не входят в этот образ.

Визуальная проверка браузером не выполнена: доступный инструмент вернул пустой список браузеров и приложений. Интерфейс проверен сборкой и lint, полный серверный путь — реальными HTTP-запросами. Нагрузочная проверка на рабочем потоке, пересчёт рабочей истории, установка служебной схемы и включение расписания остаются действиями развёртывания по `adapter/README.md`.

## Предыдущая проверка самостоятельного скрипта

17 октября 2026. Ветка `local-develop`.

Код добавлен как самостоятельный пакет; существующие сервисы, SQL-скрипт, конфигурация баз, pgAdmin и расписания не изменялись. При проверке нового кода подключения к рабочим базам `.50` и `.42` не выполнялись.

Проверки выполнены в Python 3.12 с psycopg 3.2.9 и на отдельном временном PostgreSQL 13.13 на локальном порту 25433. Рабочие SSH-туннели используют другие порты. Тестовый кластер содержит только созданные тестами базы `test_energy_source` и `test_energy_target` с вымышленными измерениями.

- 10 тестов модели: взвешивание средних отдельными непустыми счётчиками, нули/NULL, явный интервал оценки энергии, часовой пояс, даты, восстановление после простоя, контрольная отметка, проверка идентификаторов и параметров.
- 13 интеграционных тестов PostgreSQL: dry-run, сохранение существующих результатов и дней вне диапазона, идемпотентность, исправления и исчезнувшие группы, текущий незавершённый день, откат обеих витрин, пустой источник, блокировки параллельных запусков, несовпадающая схема, read-only источника, конфигурация отметки, переход летнего времени.
- 3 проверки CLI: запись требует явного решения об энергии, отсутствие DSN останавливает запуск, режим по умолчанию не запрашивает запись.
- Проверка `--help` и компиляция Python-модулей.

Всего 26 тестов прошли. Это подтверждает поведение на синтетических данных и PostgreSQL 13; производительность на рабочем потоке и реальное наполнение витрин этим выпуском не проверялись.

Расчёт энергии для нерегулярных интервалов не реализован: доступна только явно выбранная оценка по подтверждённому фиксированному интервалу либо NULL. Исправления старше окна перекрытия требуют ручного выбора диапазона. Первое применение, планировщик и переключение потребителей данных остаются отдельными действиями после проверки оператором.
