# Приложение на 193.232.208.42 с источником на 193.232.208.50

Развёртывание подготовлено в `/home/collective/smart-energy-vm42` на `.42`.
На ПК проект остаётся в обычном рабочем каталоге. Конфигурация локального
запуска через `docker-compose.yml` и `docker-compose.adapter.yml` сохранена.

## Запуск после первоначальной подготовки — две команды

На ВМ `.42`, под пользователем с доступом к Docker:

```sh
cd /home/collective/smart-energy-vm42 && sh deploy/vm42/start.sh
```

На ПК, из корня проекта:

```powershell
docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml up -d --no-build
```

Внутри института открыть **https://193.232.208.42:8443** без туннеля.
Из внешней сети через туннель открыть **https://localhost:8443**. Админка — `https://localhost:8443/admin/`,
источники — `https://localhost:8443/aggregation`. Сохраняются перенесённые
учётные записи приложения. При использовании самоподписанного сертификата
браузер может показать предупреждение. Туннель работает в контейнере после
закрытия терминала; из внешней сети нужен только SSH-порт 22, из разрешённых
внутренних сетей — TCP 8443. Сейчас в `deploy/vm42/https-allow.conf` временно
включён `allow all;`: Nginx принимает HTTPS с любого адреса, которому сеть
пропускает порт 8443. Ограничение «извне только SSH» должен обеспечивать сетевой
экран института. Вход в приложение и права пользователей сохраняются.
Для возврата фильтрации замените последнюю директиву `allow all;` на `deny all;`
и перезагрузите Nginx по инструкции в корневом README. Сохранены правила для
loopback, сетей `193.232.208.32/27`, `192.168.1.0/24` и адреса заказчика
`193.232.196.138`. Полный список подсетей сотрудников пока не подтверждён;
другие сети добавляет администратор. При NAT нужен адрес, видимый Nginx.

Если туннель на ПК остановлен и образы уже загружены, достаточно второй команды.
Эквивалентный туннель без Docker: `ssh -N -L 127.0.0.1:8443:127.0.0.1:8443 collective@193.232.208.42`.

## Подключения

| Компонент | Подключение на ВМ | Назначение |
| --- | --- | --- |
| Django `default`, `analytics`; FastAPI; adapter target/control | `127.0.0.1:25433/student` | Новая БД PostgreSQL 17 на `.42`: `student_schema` и `adapter_control` |
| Adapter source | `127.0.0.1:25432/paradigm_db`, роль `fdw_reader` | Чтение оригинала `public.electricity_sensor_readings` на `.50` |
| Django `source`; adapter directory | `127.0.0.1:25432/paradigm_db`, существующий читатель справочников | `public.sensor_directory`, `structure.*` на `.50` |
| Browser → SSH → Nginx → Django | `localhost:8443` → `.42:127.0.0.1:8443` → `127.0.0.1:15000` | Интерфейс, API, админка и статика |
| Django → FastAPI / adapter | `127.0.0.1:18001` / `127.0.0.1:18002` | Прежние внутренние HTTP API с токенами |

На `.42` при проверке обнаружен системный PostgreSQL **10.18** с базами
CMDBuild. Django 5.1 требует PostgreSQL 13 или новее
([документация Django](https://docs.djangoproject.com/en/5.1/ref/databases/#postgresql-notes)).
Поэтому приложение использует отдельный контейнер PostgreSQL 17 на той же
машине. Системный PostgreSQL, его пользователи и базы не изменяются.

Контейнеры ВМ используют `network_mode: host`: при проверке Docker bridge не
пропускал соединения к `.50`, хотя из ОС ВМ они работали. БД и внутренние сервисы
слушают `127.0.0.1`. Nginx слушает `0.0.0.0:8443`; режим доступа задаётся
в `https-allow.conf` (сейчас временно без фильтрации IP). Системный firewall
конфигурация не изменяет; межсетевой экран организации должен пропускать
8443 из внутренних сетей.
Контейнер `source-db` устанавливает SSH-туннель `.42` → `.50:22` к PostgreSQL
на `.50:127.0.0.1:5432`. Контейнер доступа на ПК устанавливает отдельный туннель
ПК → `.42:22` к Nginx. Пароли SSH читаются из файлов, ключи серверов проверяются
через закреплённый `known_hosts`. Обратное соединение от ВМ к ПК не требуется.

Архитектура React → Django → FastAPI/adapter сохраняется. Настройка
`ENERGY_ADAPTER_HOST` задаёт loopback-привязку адаптера; значение по умолчанию
вне конфигурации ВМ — `0.0.0.0`. Результаты последующего ревью адаптера,
пересчёта истории и проверки доступа описаны в [отчёте об обновлении](ADAPTER_UPDATE.md).
Роль `fdw_reader` не имеет доступа ко всем справочникам, поэтому для метаданных
используется отдельное существующее подключение, как и в локальном приложении.
FDW-объекты создавать не требуется: адаптер уже умеет читать и писать в разные БД.

## Однократная подготовка на новой установке

1. В корне проекта запустить `python deploy/vm42/configure.py`. Нужны Python 3,
   `ssh-keyscan` и OpenSSL; в Windows OpenSSL может использоваться из Git for Windows.
   Сверить показанные отпечатки SSH-ключей с администратором. Сценарий запросит
   подключения и пароли, создаст приватные настройки и сертификат. Существующие
   настройки не перезаписываются. Предоставленные для текущего развёртывания
   пароли уже сохранены в игнорируемых файлах, в Git их нет.
2. На машине с работающей сборкой Docker собрать образы:

   ```sh
   docker compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml build
   docker pull postgres:17-alpine
   docker save -o vm42-images.tar smart-energy-vm42-backend smart-energy-vm42-analytical smart-energy-vm42-adapter smart-energy-vm42-frontend smart-energy-ssh-tunnel postgres:17-alpine
   ```

3. Передать проект, `deploy/vm42/.env`, `app.env`, `secrets/`, `ssl/`, пустой
   `backups/` и архив образов на `.42` по SSH. Не включать виртуальные окружения,
   `node_modules`, `.git`, другие локальные `.env` и чужие файлы. На ВМ выполнить
   `docker load -i vm42-images.tar` из каталога с архивом. Для уже подготовленного
   развёртывания образы загружены; повторять не нужно. Архивы образов хранить вне Git.
4. Запустить две команды из первого раздела. При первом запуске `start.sh`
   сам выполняет перенос через сервис `migrate`, затем `adapter init-control`
   и запуск приложения. Перед сервисами выполняется `adapter upgrade-aggregates`:
   в существующие таблицы назначения добавляются счётчики корректных измерений.
   Старый адаптер на время обновления останавливается, данные не удаляются.
   При следующих запусках используется маркер
   `deploy/vm42/backups/restore-complete`, повторного восстановления нет.

ВМ имеет Docker Compose 1.29.2 (`docker-compose`); `start.sh` поддерживает как
его, так и современный `docker compose`. Compose 1.29 при обновлении новых
образов может выдавать `ContainerConfig`.
Для него `start.sh` пересоздаёт только frontend/backend/analytical/adapter,
сохраняя именованные тома, БД и туннель. Временная остановка приложения
входит в обычный запуск обновления.

На этой ВМ сборка пакетов внутри
контейнера не имела сетевого доступа, поэтому по умолчанию запуск использует
уже загруженные образы. `VM42_BUILD=1 sh deploy/vm42/start.sh` включает сборку
на машине, где она доступна. При обновлении перенесите и загрузите новые образы.

## Файлы конфигурации и постоянные данные

- `deploy/vm42/.env`: параметры Compose, адреса SSH и порт доступа.
- `deploy/vm42/app.env`: подключения Django/FastAPI/adapter, внутренние токены,
  разрешённые HTTP hosts/origins. Вариант заполнения — `app.env.example`.
- `deploy/vm42/secrets/`: SSH-пароли, `known_hosts`, пароль новой БД и пароль
  чтения исходной `student` только для миграции. Папка закрыта правами `700`;
  смонтированные файлы должны читаться пользователем PostgreSQL в контейнере.
- `deploy/vm42/ssl/`: сертификат и ключ Nginx.
- `deploy/vm42/https-allow.conf`: правила прямого HTTPS, сейчас временно
  `allow all;`; сохранённые правила loopback поддерживают SSH при возврате
  фильтрации IP. Для применения изменений:
  `docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml exec -T frontend sh -c 'nginx -t && nginx -s reload'`.
  Правила доступа: [документация Nginx](https://nginx.org/en/docs/http/ngx_http_access_module.html).
- `deploy/vm42/backups/student.dump`: исходный снимок, содержит данные и
  сведения пользователей; хранится приватно и не попадает в образ/Git.
- Том `smart-energy-vm42_vm42-postgres`: новая БД. Том
  `smart-energy-vm42_vm42-django-secret`: постоянный ключ Django/JWT.

При смене локального порта доступа дополните `DJANGO_CSRF_TRUSTED_ORIGINS`
в `app.env`; переменная `DASHBOARD_PORT` меняет порт ПК, `VM42_HTTPS_PORT` — порт ВМ.
`VM42_HTTPS_BIND` по умолчанию `0.0.0.0`. Для доступа по IP сертификат должен
содержать `IP:193.232.208.42` в SAN, а `DJANGO_CSRF_TRUSTED_ORIGINS` —
`https://193.232.208.42:8443`. Генератор новых настроек учитывает оба требования.
Параметры подключения и пароли не должны переноситься в отслеживаемые примеры.

## Что переносится и как проверяется

`migrate.sh` делает согласованный `pg_dump` схем `student_schema` и
`adapter_control` с `.50`. Для исходного подключения выставлено
`default_transaction_read_only=on`; выполняются только операции чтения и
необходимые pg_dump блокировки чтения. Объекты/таблицы в исходной БД не создаются
и не изменяются. Дамп сохраняется на `.42`, затем одной транзакцией
восстанавливается в новую `student` без старых владельцев и ACL.

Переносятся ORM-таблицы, пользователи и связи, миграции, сессии, сведения JWT,
обе таблицы агрегатов, профили и задания адаптера. Структура старой копии
`student_schema.electricity_sensor_readings` сохраняется, но её данные не
копируются: действующий адаптер читает оригинал с `.50`. Таким образом,
на `.42` не создаётся ещё одна копия сырья размером около 1,3 ГБ.

Сценарий отказывается восстанавливать поверх непустых схем назначения и не
перезаписывает существующий дамп. Ошибки дампа/restore останавливают запуск.
При частичном сбое сохраните дамп и проверьте новую БД; не удаляйте её вслепую.

**После первоначального переноса расписание выключено, профили неактивны и требуют проверки.**
Их история и прогресс сохранены, но старый отпечаток подключения не соответствует
новому назначению. В «Источники и агрегации» сохраните новую версию настроек,
выполните preview, затем активируйте её и включите расписание. Не подменяйте
отпечатки и не включайте старую версию прямым SQL.

При первоначальном переносе сохраняется `ENERGY_USE_STORED_ENERGY=0`.
31.10.2026 после проверки истории на действующей `.42` включены сохранённая
энергия (`1` в Django и аналитике), новый проверенный профиль и ежедневное
расписание. Непроверенные старые агрегаты сохранены с предупреждением;
подробности — в [отчёте](ADAPTER_UPDATE.md). Новая установка требует собственной
проверки перед таким переключением. Копирование ключа подписи Django со старого
развёртывания не выполняется: пользователи сохраняются, но нужен новый вход.

На 30.10.2026 проверены совпадение количества строк служебных таблиц,
сумм энергии/точек обеих витрин (10 475 часовых, 518 суточных строк), перенос
14 пользователей, шесть dashboard API и HTTP-запрос сравнения периодов
Django → FastAPI. Чтение сырья подтверждено под `fdw_reader` с SELECT без INSERT,
справочник содержит 181 запись; обследование вернуло 38 столбцов и 5 примеров.
HTTPS через туннель ПК вернул 200 с проверкой сертификата.

Это снимок на момент переноса. Прежние развёртывания и писатели `.50` автоматически
не выключаются; последующие изменения там не реплицируются в новую БД.

## Диагностика и остановка

На ВМ, из корня проекта:

```sh
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml ps
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml logs --tail=100 backend adapter source-db
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml down
```

На ПК остановить доступ:

```powershell
docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml down
```

При обычной остановке не использовать `down -v`: он удаляет том БД и ключ Django.
Для отката можно остановить новое развёртывание и вернуться к прежнему; данные
источника не изменены. Записи, появившиеся только в новой БД, требуют отдельного
переноса перед откатом.

Проверки разработки: `python -m unittest discover -s deploy/vm42 -p test_configuration.py`
и `docker compose -p smart-energy-adapter-tests -f adapter/tests/compose.yml run --build --rm tests`.
