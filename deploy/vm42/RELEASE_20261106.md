## Сборка на этой ВМ

На ВМ установлен Compose v1 1.29.2. Стандартная сеть сборки не смогла
разрешить PyPI; сборка выполнена с отдельным overlay внутри проекта:
`deploy/vm42/updates/release-20261106/build-network.yml`.
В нём только `build.network: host` для четырёх образов, без изменения
настроек Docker daemon, firewall или рабочих сетей. Исходный VM Compose сохранён.

Для повторной сборки установленного кода:

```sh
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env \
  -f docker-compose.vm42.yml \
  -f deploy/vm42/updates/release-20261106/build-network.yml \
  build adapter backend analytical frontend
```

Для обычного перезапуска без изменения кода сборка не нужна.
При обновлении образов Compose v1 сначала остановить/удалить только контейнеры
приложения по инструкции обновления; БД и её тома сохранять.

## Отчёт датчиков и доступ

Отчёт использует новый активный проверенный профиль ВМ. Для climate/meteo
в приватном `app.env` заданы существующие read-only подключения:

```dotenv
ENERGY_AVAILABILITY_SOURCES={"climate":{"connection":"directory"},"meteo":{"connection":"directory"}}
```

У электрического подключения есть SELECT только на электрическое сырьё;
`directory` имеет необходимые права на климатические/метеоданные.
Новые права источнику не выдавались. Явный локальный ID профиля не копировался.

При проверке обнаружены реальные обрывы SSH ВМ42 → ВМ50: журнал существующего
`source-db` содержит `Host is unreachable`/`Operation timed out`, а чтение
через 25432 получило `Connection refused`. Туннель автоматически восстановил
подключение к 22:22 Москве; после этого планы SQL всех трёх источников
снова прочитаны. Сети/службы ОС и источник ВМ50 не изменялись.

Первые проверки истории отчёта завершились `partial`, все 181 устройство
получили `unknown`, а не ложное «нет данных». Первая исчерпала общий лимит
600 секунд (19 суточных чтений), вторая закончилась через 362 секунды
с ошибками источников. После восстановления запущено новое чтение;
на 22:23:50 оно ещё `pending`. Полный `ready` на ВМ пока не подтверждён.
Это не блокирует worker, но новые SQL-запросы и ночной пересчёт зависят
от доступности внешнего источника. Не считать Docker health постоянной
гарантией стабильности сети: туннель может восстановиться между проверками.

Для scheduled-заданий уже предусмотрено до пяти попыток с паузой 5 минут
при `psycopg.OperationalError`; запись и прогресс сохраняются транзакционно.
Отдельный новый тест фактического worker подтвердил: после обрыва задание
снова в очереди с задержкой, старые строки/прогресс целы; при восстановлении
вторая попытка успешно записывает день без дубликатов. Общая сеть за пределами
проекта остаётся внешним ограничением; обещание безусловной ночной записи
при недоступном источнике было бы неверным.

На ПК уже запущен штатный SSH-доступ к ВМ на **https://localhost:8444/**,
так как 8443 занят локальной версией. HTTPS и новый frontend через него
проверены. Прямой HTTPS к адресу ВМ из текущей сети не установился;
сетевые ограничения не менялись.

Для повторного запуска этого доступа из PowerShell:

```powershell

docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml up -d --no-build
```
