Отчёт добавлен к исходникам ветки fix/available-energy-aggregates. Новых
миграций, колонок энергетических таблиц и фонового расписания он не требует.
Обновляются backend, adapter и frontend. Порядок обновления пересчёта описан
отдельно в deploy/vm42/AGGREGATION_UPDATE.md, если он ещё не установлен.

06.11.2026 backend, adapter и frontend установлены на ВМ42 вместе с новой
версией пересчёта. Фактическая конфигурация источников, резервная копия и
результаты проверок: [отчёт ВМ](../../../deploy/vm42/RELEASE_20261106.md).

## Настройка

Нужен сохранённый проверенный профиль электрического источника с текущим
fingerprint. Для отчёта использовать его активную версию либо добавить
ENERGY_AVAILABILITY_PROFILE_ID=<полный ID> в приватный env адаптера.
Явный ID не активирует профиль для записи и не включает расписание.
Нельзя копировать локальный ID вслепую на ВМ: выбрать проверенный профиль
в её собственной служебной схеме. Права источников — SELECT.

Для climate/meteo подключение берётся из того же источника. По умолчанию
используются public.climate_sensor_data и public.meteo_sensor_data.
При иных адресах/названиях разрешена серверная переменная
ENERGY_AVAILABILITY_SOURCES с JSON, например:

```json
{"climate":{"table":"public.climate_sensor_data","connection":"paradigm","source_timezone":"Europe/Moscow"},"meteo":{"table":"public.meteo_sensor_data","connection":"paradigm"}}
```

Это псевдонимы из существующего серверного реестра, не DSN. В браузере они
не выбираются. Типы устройств определяются по device_list/device_type,
справочник и комнаты читаются по directory_connection профиля.
Климатические поля: co2, humidity, light, motion, temperature; meteo:
baropressure, dewpoint, humidity, temperature, winddirection, windspeed.
Существующие числовые столбцы неверного типа дают ошибку проверки источника;
отсутствующие необязательные поля не подменяются нулями.

## Локально

Для уже подготовленного workstation развёртывания:

```powershell
docker compose -p smart-energy-workstation -f docker-compose.local.yml build adapter backend frontend
docker compose -p smart-energy-workstation -f docker-compose.local.yml up -d --no-deps adapter backend frontend
```

Сайт https://localhost:8443, блок «Состояние датчиков» под карточками KPI.
Перед обновлением adapter убедиться, что выполняющийся apply завершён;
очередь новой проверки отчёта от writer полностью отдельна.
Для этой рабочей станции ID проверенного профиля добавлен в приватный app.env.

## Самостоятельное обновление ВМ

Использовать существующий отдельный VM42 Compose и его приватный app.env.
Не смешивать его с docker-compose.local.yml. Добавить ID профиля при необходимости.
Сохранить прежние env, секреты, control/energy данные и образы для отката.
После доставки комплекта исходников с обновлённым frontend-dist.tar.gz выполнить
штатную сборку/обновление только backend, adapter, frontend средствами VM42.
Приватные настройки и сети доступа ВМ не заменять локальными файлами.
Если на ВМ пересчёт ещё старой версии, сначала выполнить его отдельную инструкцию.

Проверить вход обычного пользователя, наличие блока, полный каталог устройств,
три периода, предупреждение при нехватке эталонной истории и прежние графики.
Отчёт не исправляет состав ранее записанных энергетических агрегатов.
При откате восстановить предыдущие образы этих сервисов; данных новой ORM нет.
Существующие таблицы отчёт только читает, обратная миграция не нужна.

## Актуальность и диагностика

Первый запрос запускает фоновое чтение; UI опрашивает результат каждые 3 секунды.
Проверка истории может занимать несколько минут. Одновременно читается один
отчёт, ожидают максимум три периода. Максимум 120 с на SQL, 600 с на всю проверку.
Кеш готового результата — 10 минут; явное обновление допускается не чаще
30 секунд после завершения предыдущего. Показывается время фактической проверки.
Переключатели периодов используют общий кеш суточных статистик (10 минут на
момент чтения); при использовании кеша UI показывает его исходное время.
Явное обновление перечитывает статистику, соблюдая ограничение частоты.
Кеш находится в памяти адаптера, исчезает при перезапуске и не записывается
в jobs/events, управляющую БД или энергетические витрины.

Внутренний GET /device-availability?period=day|week|month требует существующего
X-Internal-Token. Публичный Django GET
/api/consumption/dashboard/device-availability/ требует авторизации обычного
пользователя. Управление пересчётом остаётся только для сотрудников.

В ответе: state pending/ready/partial/error/busy; rows и summary у готового
результата; интервалы from/to_exclusive/history_from/history_to_exclusive,
checked_at, причины неизвестных результатов и ошибок источников без секретов.
Логи чтения доступны через стандартный docker compose logs adapter.

«Мало данных» означает менее 90% исторического эталона по числу пригодных
уникальных временных меток. Это не доля времени работы. NULL/0 игнорируются
только в этом отчёте; нулевое потребление в агрегатах не меняется.
История для эталона исключает проверяемый период. Если её недостаточно,
положительные измерения не объявляются нормой без эталона: статус unknown.
Точно установленное отсутствие пригодных измерений остаётся no_data.
