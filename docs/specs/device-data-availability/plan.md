# План: отчёт о доступности устройств

Статус: реализация разрешена после согласования правил. Ветка:
fix/available-energy-aggregates. Основание: [spec.md](spec.md), [ui.md](ui.md).
Существующие формулы/запись/расписание агрегатов сохраняются.

## 1. Архитектура

Браузер → авторизованный Django API → приватный reader adapter → исходные
показания и справочник. Ответ содержит сводку всех устройств; поиск, тип,
состояние и пагинация выполняются на клиенте для небольшой выборки справочника.
Клиент получает только статистику, без сырых строк, DSN и параметров подключения.

Reader не использует writer jobs, управляющие задания или энергетические витрины.
Единственный фоновый поток выполняет ограниченные SQL-запросы по дням.
До завершения HTTP возвращает pending, браузер опрашивает через 3 секунды.
Открытие панели не блокирует HTTP-потоки, health и очередь агрегирования.
Одновременно ожидают максимум три проверки периодов. Перезапуск теряет только
кеш: повторная проверка возможна, рабочие данные не меняются.
Для переключения периодов переиспользовать суточные статистики не старше 10 минут
на момент чтения из кеша; ключ — хеш источника/подписи/SQL и день. Максимум 400
записей кеша. Явное обновление читает дни заново. В ответе и UI отдельно показать
data_checked_from, если результат использует сохранённую статистику.

## 2. Конфигурация и источники

Новый adapter/availability.py использует проверенный профиль электрического
источника: активный либо явно заданный ENERGY_AVAILABILITY_PROFILE_ID.
Явный ID не активирует writer и не включает расписание. Проверять validated
и fingerprint; переиспользовать source_cte/source_capabilities/build_settings.
Измерения масштабируются по подтверждённым mappings; неполные фазы не сливаются.

Из справочника читать все устройства через LEFT JOIN device_list/device_type,
сохранять ID и проверять уникальность имён. Тип выбирать по метаданным.
Неизвестный тип получает unknown, а не отсутствие показаний.

Климат и метеостанция по умолчанию используют public.climate_sensor_data и
public.meteo_sensor_data в подключении источника. Серверные переопределения
ENERGY_AVAILABILITY_SOURCES разрешают только table/connection/source_timezone
для этих двух типов; поля показателей фиксированы, проверяются их типы/доступность.
Таблицы и идентификаторы экранировать psycopg.sql.Identifier, значения связывать.
Никаких параметров подключения из браузера.

## 3. SQL и классификация

Для каждого типа читать базовые 30 дней перед периодом и сам период. Выполнять
суточные запросы с индексным диапазоном [start,end), чтобы не сортировать
месячный объём сырых показаний в одном запросе. Группировать sensor_name/ts:
BOOL_OR пригодности, одна временная метка — один голос. Передавать только
суточные counts, last_valid и медиану положительных интервалов временных меток.

Контракт пригодности и автоматический эталон — spec.md D5–D8.
Обычный суточный уровень = медиана 30 чисел с нулевыми днями. Минимум 21
положительный день в ±20% уровня. Частота = медиана суточных медиан
положительных интервалов исходных уникальных времён, включая пакеты NULL/0.
Аналоги: та же модель, частота отличается не более 20%, стабильная история.
Минимум 3 аналога → медиана их уровней; иначе свой уровень при стабильности.
Эталон умножается на число дней периода. Порог строго <90%, сравнение Decimal.

Нет пригодных записей → no_data. Пригодные есть, эталон неизвестен → unknown.
Ниже порога → low_data, иначе ok. Ошибка источника даёт unknown только
соответствующим типам; частичный результат явно обозначен partial.
Процент может быть выше 100: это относительное количество, не доля времени.

## 4. Нагрузка и актуальность

Read-only сессии, connect_timeout 8 с, запрос максимум 120 с, вся проверка
максимум 600 с. Ошибка/таймаут не превращается в no_data. Переменные доступа
и внутренние исключения не возвращать клиенту.

Кеш готового ответа — 10 минут, ошибка — 30 секунд; явное обновление допускает
новую проверку не чаще чем через 30 секунд после завершения предыдущей.
Ключ включает московский день, период, служебную схему и ID профиля.
После полуночи результат прошлого периода не используется. Дубликаты запросов
объединяются. На UI показывать фактические границы и checked_at.

## 5. API и интерфейс

- Adapter: только внутренний GET /device-availability?period=day|week|month,
  refresh=0|1. Существующая аутентификация X-Internal-Token сохраняется.
- Django: GET /api/consumption/dashboard/device-availability/, IsAuthenticated.
  Новый availability_views.py; только period и refresh, никаких SQL/источников.
  apps/aggregation/AdapterView остаётся staff-only.
- React: DeviceAvailabilityPanel.jsx в DashboardOverviewPage под KPI.
  Состояние отчёта отделено от верхних фильтров потребления; новый feature API
  использует существующий JWT/credentials/refresh flow.
- Отменять предыдущий запрос и игнорировать его результат при смене периода.
  Ошибка энергопотребления не скрывает отчёт климатических устройств.
- Макет, поиск/тип/пагинация и mobile/dark — ui.md.

## 7. Верификация и поставка

Изолированный PostgreSQL: все типы, нули/NULL/NaN/Infinity, уникальные времена,
неполные фазы, 90%/89%, 21/20 дней, разные модели/частоты, свой исторический
эталон и отсутствие истории, частичный отказ источника, read-only.
API: обычный пользователь/неавторизованный, валидация, невозможность управления.
UI: фильтры, поиск по полной выборке, пагинация, polling, старый запоздалый
ответ, независимость потребления, Москва при другом timezone, desktop/mobile,
две темы и клавиатура. Выполнить старые тесты расчётов и новый замер нагрузки.

Локальный Docker обновить после проверок; фактическое чтение источников
выполнять только через новый read-only отчёт. На ВМ подготовить инструкцию
самостоятельной установки без фактического развёртывания.
