# Спецификация: доступность данных устройств

Статус: правила согласованы; реализация разрешена пользователем в той же ветке.
Дата: 2026-11-05.
Ветка: fix/available-energy-aggregates. Существующую логику менять только при необходимости.
Связанные документы: [plan.md](plan.md), [tasks.md](tasks.md).
Корневые spec.md/plan.md/tasks.md описывают предыдущий пересчёт и сохраняются.

## 1. Цель

Показывать устройства, от которых за выбранный период не поступали пригодные
измерения либо измерений было мало. Пользователь выбирает день, неделю или месяц
и получает список проблемных устройств с объяснением результата.

## 2. Подтверждённые решения

| ID | Решение пользователя |
| --- | --- |
| D1 | Все устройства справочника, включая климатические датчики и метеостанцию. Сейчас их 181; число не является константой приложения. |
| D2 | Последние завершённые 1 / 7 / 30 дней по Москве. Текущий неполный день не включается. |
| D3 | Электросчётчик с записями, но без корректной мощности за период, показывать как «нет данных». |
| D4 | Блок на главном дашборде для всех вошедших пользователей; отдельный удобный селектор режима поиска проблемных датчиков. Представление информации пользователь поручил спроектировать самостоятельно. |
| D5 | «Мало данных» — строго менее 90% эталона. Ровно 90% допустимо. Дополнительный порог 10% не вводится. |
| D6 | NULL, числовой 0 и некорректные значения не являются пригодными измерениями в новом отчёте. Существующие агрегаты сохраняют собственную семантику корректного нуля. |
| D7 | Для климатического устройства/метеостанции достаточно одного пригодного измерения окружающей среды в записи. |
| D8 | Автоматический эталон по истории: 30 дней до проверяемого периода, минимум 21 стабильный день с отклонением количества не более 20%; медиана сопоставимых устройств, при числе менее трёх — собственная стабильная история, иначе эталон неизвестен. Пользователь подтвердил предложенное правило. |

D3 не означает, что NULL отдельной записи отменяет остальные пригодные
измерения. Пригодность оценивается для каждой записи, затем считается количество.
Полнота отчёта — относительное количество пригодных временных меток, а не
доля времени работы и не доказательство физической поломки.

Эталон: для каждого устройства взять суточные количества пригодных уникальных
временных меток за 30 предшествующих дней, включая дни с нулём. Обычный суточный
уровень — медиана этих 30 количеств. Стабильность: минимум 21 положительный день
в пределах ±20% этого уровня. Частота передачи оценивается по медиане положительных
интервалов уникальных временных меток базовой истории, включая NULL/0-пакеты:
медиана суточных медиан. Сопоставимость — одна модель и отличие частоты не более
20%. Эталон = медиана обычных уровней минимум трёх стабильных устройств × число
дней отчёта. При нехватке аналогов используется свой уровень, только если
история стабильна. Проверяемый период никогда не участвует в выборе эталона.

При отсутствии эталона нулевое количество пригодных записей всё равно означает
«нет данных»; при положительном количестве статус — «эталон не определён».
Это статистическая оценка по истории, а не паспортная частота. Группа стабильно
плохо передающих устройств может иметь заниженный эталон; отсутствие независимой
опоры нельзя скрывать утверждением о физической исправности.

## 3. Исследованные факты

- В public.sensor_directory текущей БД — 181 уникальный ID и 181 уникальное
  имя: 153 электросчётчика и 28 устройств других типов. Связь типа задаётся
  через device_listid → public.device_list → public.device_type.
- Источники показаний существуют раздельно:
  public.electricity_sensor_readings, public.climate_sensor_data,
  public.meteo_sensor_data. У каждой таблицы есть ts и sensor_name.
  Каталог таблиц проверен в режиме чтения; наполненность климатических
  источников и соответствие моделей этим таблицам ещё не проверялись.
- Электрические агрегаты содержат points_count и отдельные counts пригодных
  значений каждой метрики. Новый writer объединяет повторы времени, но
  legacy-строки могли быть рассчитаны по другой логике.
- points_count > 0 не доказывает пригодность измерений: все измеряемые значения
  могут быть NULL. Измеренный ноль является пригодным показанием.
- Отсутствие агрегатов само по себе не доказывает отсутствие исходных показаний:
  пересчёт мог не выполняться или завершиться ошибкой.
- В нынешнем отчёте дашборда нет отдельного API доступности всех типов устройств.
  Приватные операции adapter сейчас доступны через staff-only gateway;
  обычные отчёты дашборда требуют аутентификации.

## 4. Функциональные требования

### FR-01. Состав устройств

Получать полный состав из справочника, включая устройства без единого показания
в выбранном периоде. Не ограничивать список устройствами, найденными в показаниях
или витринах. Различать типы устройств и выбирать соответствующий источник.
Уникальность опирать на идентификатор устройства в справочнике и проверенную
связь с исходными именами, а не на число строк после JOIN.
Не объединять разные устройства по похожим отображаемым именам.

Выбор всех устройств относится к этому отчёту. Он не предписывает записывать
климатические устройства в энергетические витрины. Ранее выявленное расширение
энергетических витрин до 181 требует отдельного решения о составе электросчётчиков.

### FR-02. Периоды

Фильтры: «День», «Неделя», «Месяц» = 1 / 7 / 30 завершённых московских дней.
Диапазон [начало, конец), конец — сегодняшняя полночь в Europe/Moscow.
Показывать пользователю фактические календарные границы периода.

Пример на 05.11.2026: день — 04.11; неделя — 29.10–04.11;
месяц — 06.10–04.11 включительно. Часовой пояс браузера не меняет границы.

### FR-03. Пригодность данных

Для электросчётчика использовать контракт активной мощности существующего
приложения: пригодное общее значение либо все три пригодные фазы одной записи;
NULL и нечисловые/нефинитные значения не являются пригодной мощностью.
В новом отчёте общая мощность должна быть конечной и отличной от 0.
Это не меняет пригодность нулевого потребления в агрегатах. Нельзя синтезировать три фазы
из разных конфликтующих записей одного времени.

Если пригодной мощности за весь период нет, статус — «нет данных», даже если
записи поступали. Причина должна объяснять, отсутствовали ли сами записи или
они не содержали пригодных измерений. Это единый пользовательский статус
с объяснением, а не самостоятельный статус «исправен, но NULL».

Для климатических устройств учитываются CO₂, влажность, освещённость, движение,
температура; для метеостанции — давление, точка росы, влажность, температура,
направление/скорость ветра. Батарейное напряжение и служебные поля не доказывают
наличия измерений окружающей среды. Нужен хотя бы один конечный ненулевой показатель.
Для одного устройства и времени учитывается одна запись: она пригодна, если
хотя бы один повтор содержит пригодное измерение по правилам своего типа.
Дубликаты не должны создавать видимость нормального поступления данных.

### FR-04. Достоверность результата

Ошибка подключения, неизвестный источник, неподтверждённая схема или недостаток
сведений об ожидаемом интервале должны явно отличаться от отсутствия показаний.
При отказе чтения не объявлять все устройства молчащими или исправными.
Если используется производная статистика, обозначать период её фактической
проверки, актуальность и ограничения; непересчитанный период не считать нулевым.
Для всех типов используются исходные показания независимо от пересчёта;
это техническое решение обеспечивает проверку климатических источников,
которые не представлены в электрических агрегатах.

### FR-05. Представление

На главном дашборде разместить блок «Состояние датчиков», доступный всем
аутентифицированным пользователям, включая пользователей без is_staff.
Чтение отчёта не предоставляет прав на управление адаптером и пересчёт.

В рамках делегированного проектирования интерфейса выбран следующий вариант:

- Отдельная панель внутри блока: переключатель «Все проблемы / Нет данных /
  Мало данных» и собственный переключатель «День / Неделя / Месяц».
  По умолчанию выбраны все проблемы и день. Это представление списка устройств;
  верхние фильтры и графики потребления сохраняют собственное состояние.
- Отдельные показатели количества устройств без данных, с малым количеством
  и тех, которые не удалось проверить; общее число берётся из справочника.
- Компактный список: устройство и тип, помещение при наличии, текстовый статус
  и причина, число пригодных измерений, процент от эталона при известном эталоне,
  последнее пригодное измерение в выбранном периоде. Неприменимые поля — «—».
- Поиск по имени/ID, фильтр типа устройства, вывод по 10 строк с пагинацией.
  Фильтры списка применяются ко всем устройствам отчёта, а не только к текущей
  странице. Сводные показатели относятся ко всему периоду, подпись списка
  показывает количество найденных по его фильтрам.
- Порядок: сначала без данных, затем мало данных по возрастанию полноты;
  одинаковые значения упорядочиваются стабильно по имени/ID. Неизвестные
  результаты показаны отдельным заметным сообщением и раскрываемым списком.
- Фактические даты Москвы и время проверки расположены рядом с переключателями.
  NULL последнего измерения обозначает отсутствие пригодного в этом периоде,
  а не утверждение «никогда не присылал».

Текстовые причины различают «нет записей», «записи без пригодных измерений»
и техническую невозможность проверки. Название «молчащий» не используется
как доказательство физической поломки. Отдельной отметки «критически мало» нет.
Визуальная схема, состояния и адаптация: [ui.md](ui.md).

## 5. Нефункциональные требования и ограничения

- Источники и справочники читать без изменения. Просмотр отчёта не запускает
  пересчёт, не меняет расписание и не заменяет агрегаты.
- Проверять доступ на сервере. В браузер не передавать секреты, DSN,
  произвольные SQL/имена источников. Сохранить существующий JWT/refresh flow.
- Одинаковый период и снимок источника дают одинаковые результаты при
  перестановке и повторной доставке идентичных записей.
- Передавать в браузер сводку, а не сырые показания за месяц.
- Ограничить диапазон и время запросов; повторные запросы не должны создавать
  неконтролируемую нагрузку на рабочий источник. Конкретную стратегию кеша/
  фонового расчёта выбрать в плане после решения Q6 и замера.
- Хранить суммы/нулевые/неизвестные значения без подмены NULL на 0.
- Проверки с записью выполнять только на изолированных фикстурах.
- Подготовить UI-сборку и Docker-архив для последующей самостоятельной
  установки на ВМ. Фактическая установка на ВМ в этот этап не включена.

## 6. Предварительные критерии приёмки

1. Переключатели дают ровно 1/7/30 завершённых московских дней, включая
   переход месяца/года и браузер с другим часовым поясом.
2. Ожидаемое устройство без исходных строк остаётся в отчёте.
3. Климатические устройства проверяются по своему источнику, а не по
   наличию строки в electricity_sensor_readings.
4. Все NULL/0 мощности дают «нет данных» в отчёте без изменения энергетического расчёта.
   Частичные фазы разных строк не образуют пригодную общую мощность.
5. Точные повторы и одинаковое время одного устройства не увеличивают
   доступность; разные устройства с одним временем не объединяются.
6. Ошибка источника и непересчитанная витрина не дают ложный статус
   «не присылал данные». Старый кеш явно обозначен.
7. Пригодное и непригодное показание одного времени не теряют пригодный
   результат; значение и количество определяются единым согласованным правилом.
8. UI показывает проблемы, отсутствие проблем, незавершённую проверку и ошибку
   различимыми состояниями. Итоги и список не расходятся после фильтрации.
9. Прямой запрос API соблюдает согласованные права доступа.
10. Проверка не изменяет источники, энергетические агрегаты и расписание.
11. Проверены ровно 90%, ниже и выше порога, 21/20 стабильных дней, разные
    модели/частоты, одиночная метеостанция и отсутствие предшествующей истории.
12. На месячном диапазоне выполнен замер запросов; согласованы допустимая
    задержка и актуальность. Таймаут не превращается в отсутствие показаний.
13. Обычный вошедший пользователь видит блок и может получить отчёт напрямую
    через API; неавторизованный пользователь доступа не имеет. Управление
    адаптером по-прежнему требует is_staff.
14. Переключение периода и состояния в блоке не изменяет период, дату,
    выбранный электросчётчик и графики потребления. Выбор электросчётчика
    в верхнем фильтре не ограничивает отчёт всех типов устройств.
15. Быстрое переключение фильтров не подменяет новый результат запоздавшим
    ответом старого запроса. Поиск, пагинация и итоговое количество согласованы.
16. На desktop/mobile, в светлой/тёмной теме доступны подписи, текстовые статусы
    и управление с клавиатуры; смысл не передаётся только цветом.

## 7. Авторизация и границы

Пользователь разрешил реализацию после уточнений в той же ветке и подтвердил
правило автоматического эталона. Q1–Q10 закрыты принятыми решениями и описанной
технической политикой. Повторное подтверждение тех же решений не требуется.

Проверка выполняется отдельно от writer; read-only источники, ограниченные
суточные SQL-запросы, один фоновый reader и кеш ответа. Миграции энергетических
таблиц для этой фичи не нужны. Не изменять прежние расчёты и расписание.
Результаты проверок и ограничения поставки фиксируются в tasks.md.
