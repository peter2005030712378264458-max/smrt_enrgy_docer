# Руководство администратора Smart Energy

Документ предназначен для администратора приложения и оператора пересчёта.
Описывает текущий код, а для существующей ВМ42 — зафиксированное обновление
от 06.11.2026. Текущее состояние работающих сервисов всегда проверяйте отдельно.

Первоначальная установка: [INSTALLATION.md](INSTALLATION.md).
Объяснение пользовательских экранов: [USER_GUIDE.md](USER_GUIDE.md).

## 1. Роли и зона ответственности

| Роль | Возможности |
| --- | --- |
| Обычный активный пользователь | Дашборд, связи, аналитика, состояние датчиков, собственные уведомления/отчёты |
| Персонал, `is_staff=True` | Дополнительно управление источниками, профилями, пересчётом и расписанием |
| Суперпользователь Django | Управление пользователями и всеми доступными объектами Django Admin |
| Системный администратор с SSH/Docker | Запуск сервисов, env/секреты, резервное копирование, миграции, обновление |

Статус персонала приложения не даёт автоматически доступ к SSH или Docker.
В Django Admin обычному staff нужны соответствующие разрешения для конкретных
объектов; суперпользователь имеет полный административный доступ.

Источники на ВМ50 используются только для чтения. Обычное обслуживание
не требует изменения системного PostgreSQL/CMDBuild, ОС или файлов вне
`/home/collective/smart-energy-vm42`.

## 2. Архитектура и конфигурация

```text
Браузер → HTTPS/Nginx → Django
                         ├─ PostgreSQL приложения: пользователи, отчёты, агрегаты
                         ├─ FastAPI: статистическое сравнение
                         └─ Adapter
                             ├─ writer: очередь → чтение сырья → две витрины
                             ├─ scheduler: постановка суточных/повторных заданий
                             └─ отдельный reader: отчёт состояния датчиков

Notifications → Django ORM + агрегаты / live-reader → SMTP
```

На ВМ42 используются Compose-проект **`smart-energy-vm42`**, отдельный
PostgreSQL 17 на 25433 и туннель `source-db` к источнику на 25432.
Внутренние HTTP-сервисы слушают loopback: Django 15000, аналитика 18001,
adapter 18002. Сетевой вход — Nginx на 8443.

Основные данные в `student`:

| Место | Что хранится |
| --- | --- |
| `student_schema` | ORM-таблицы приложения и две таблицы энергетических агрегатов |
| `adapter_control.profiles` | Версии профилей, валидация, активность и границы прогресса |
| `adapter_control.jobs` | Задания и JSONB-журнал `events` |
| `adapter_control.settings` | Расписание и версия control-схемы |
| `adapter_control.day_results` | Последний результат записи/пропуска по профилю и дате |

На workstation каждая установка использует свою схему
`adapter_ws_v3_<случайный ID>`, но общие энергетические таблицы сервера.
Не копируйте локальный ID очереди на другую машину и не включайте второго
независимого writer по тому же назначению без согласованного порядка работы.

### 2.1. Где находятся настройки

| Файл/том | Назначение |
| --- | --- |
| `deploy/vm42/.env` | Подстановка переменных VM Compose |
| `deploy/vm42/app.env` | БД, внутренние токены, HTTP hosts/origins, SMTP, параметры adapter |
| `deploy/vm42/secrets/` | Пароли и проверенные ключи SSH |
| `deploy/vm42/ssl/` | Сертификат и приватный ключ Nginx |
| `deploy/vm42/https-allow.conf` | Правила прямого HTTPS-доступа |
| `smart-energy-vm42_vm42-postgres` | Данные PostgreSQL приложения |
| `smart-energy-vm42_vm42-django-secret` | Постоянный ключ подписи Django/JWT |
| `deploy/local/app.env`, корневой `.env` | Настройки workstation и её уникальной очереди |

Compose `environment` имеет приоритет над сервисным `env_file`.
Не публикуйте полный вывод `docker compose config`, `docker inspect` с env
или содержимое приватных файлов: там могут быть реквизиты.

При изменении env нужно пересоздать затронутые контейнеры. Обычный
`restart` перечитывает не все параметры, заданные при создании контейнера.

### 2.2. Внутренние токены и энергия

- Django/FastAPI должны иметь совпадающий токен аналитики:
  `ANALYTICS_SERVICE_TOKEN` с предусмотренным fallback `ANALYTICS_INTERNAL_TOKEN`
  на стороне gateway и `ANALYTICS_INTERNAL_TOKEN` в аналитике.
- Django и adapter должны использовать один `ENERGY_ADAPTER_TOKEN`;
  adapter требует минимум 24 символа. Токен не передаётся браузеру.
- `ENERGY_USE_STORED_ENERGY` должен совпадать у Django и аналитики.
  На существующей ВМ42 используется 1. Переход новой установки с 0 на 1
  требует проверки/пересчёта истории, а не только перезапуска контейнеров.
- При изменении HTTPS-адреса проверьте `DJANGO_ALLOWED_HOSTS` и
  `DJANGO_CSRF_TRUSTED_ORIGINS`, включая фактический порт.

## 3. Управление пользователями

Откройте `/admin/` по рабочему HTTPS-адресу. Это отдельная сессия Django Admin;
вход в пользовательский интерфейс не заменяет административный вход.

1. Войдите суперпользователем.
2. Откройте пользователя по email.
3. Для допуска к пересчёту включите **«Статус персонала»** (`is_staff`).
4. Для блокировки доступа снимите **«Активен»** (`is_active`).
5. Сохраните и попросите пользователя обновить страницу/повторить вход.

Не назначайте суперпользователя только ради доступа к пересчёту.
При утрате пароля используйте штатную смену пароля в Admin либо
интерактивную команду `changepassword`; не записывайте открытый пароль SQL-запросом.

В примерах далее на ВМ используется функция-сокращение:

```sh
cd /home/collective/smart-energy-vm42
compose() {
  docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml "$@"
}
```

Определите её в каждом новом терминале. На системе с Compose v2 замените
`docker-compose` внутри функции на `docker compose`, сохранив аргументы.

```sh
compose exec backend python manage.py createsuperuser
compose exec backend python manage.py changepassword user@example.org
```

Первая команда создаёт нового администратора, вторая меняет пароль
существующего пользователя с таким email. Реальный email замените на нужный.

## 4. Источники и профили

### 4.1. Что должно быть готово

Проверьте доступность исходной таблицы, справочника устройств, назначения
и control-схемы. На источнике нужны SELECT, на назначении — права writer.
Основные подключения заданы серверными переменными:

- `ENERGY_AGG_SOURCE_DSN` — сырьё;
- `ENERGY_AGG_TARGET_DSN` — витрины;
- `ENERGY_AGG_DIRECTORY_DSN` — отдельный читатель каталога, если нужен;
- `ENERGY_ADAPTER_CONTROL_DSN` — отдельная control-БД, если используется;
  иначе служебные таблицы находятся в target.

В профилях выбираются псевдонимы подключений, а не открытые пароли/DSN.
`directory_connection` профиля имеет приоритет над подключением справочника
по умолчанию. Один активный профиль определяет автоматический writer.

### 4.2. Новый источник через интерфейс

На странице **«Источники и агрегации»** откройте **«Источник и соответствия»**:

1. Выберите подключение и имя таблицы вида `public.electricity_sensor_readings`.
2. Нажмите **«Обследовать источник»**, дождитесь задания.
3. Изучите структуру, типы, доступность полей и примеры.
4. Примените предложения и вручную подтвердите смысл каждого соответствия.
5. Укажите единицы/множители, исходный часовой пояс и подтверждённый интервал.
6. Проверьте справочник и, при необходимости, `sensor_map`.
7. Отметьте подтверждение и нажмите **«Сохранить новую версию»**.

Сохранение создаёт версию, не переписывая предыдущую. Оно не рассчитывает
агрегаты, не активирует профиль и не включает расписание.

Для текущего источника подтверждён интервал **5 секунд**, окно алгоритма —
**10 секунд**. Это разные настройки. Не заменяйте исходный интервал размером
окна: он используется при расчёте известных вкладов энергии.

Примеры множителей: кВт → Вт — 1000, мА → А — 0.001.
По имени столбца нельзя надёжно определить единицу измерения.
Накопительный регистр энергии не заменяет мгновенную мощность в этом алгоритме.

### 4.3. Дополнительные PostgreSQL-подключения

Если серверу настроены зашифрованный реестр и отдельный ключ, staff может
выбрать **«＋ Добавить подключение…»**, указать псевдоним, адрес, порт,
БД, пользователя, пароль и SSL. Проверка выполняется в режиме чтения.

Workstation Compose монтирует для этого `adapter-state` и
`deploy/local/private/connection_key`. Для другой установки поддержка
должна быть настроена явно через `ENERGY_ADAPTER_CONNECTIONS_FILE` и
`ENERGY_ADAPTER_CONNECTION_KEY_FILE`. Наличие формы само по себе не доказывает
готовность приватного хранилища.

Сохранение подключения не меняет target, метаданные дашборда или активный профиль.
Для изменения существующего подключения создаётся новый alias и новая версия
профиля. Для восстановления реестра нужны **и зашифрованный файл, и исходный ключ**.

## 5. Ручной пересчёт агрегатов

### 5.1. Безопасный порядок работы

1. Убедитесь, что выбрана нужная версия профиля и правильное назначение.
2. Если пересчёт может пересечься с серверным/локальным writer, согласуйте
   единственного обработчика; для обслуживания выключите автоматическое расписание.
3. На вкладке **«Пересчёт»** задайте **«С даты включительно»** и
   **«До даты, не включая»**.
4. Запустите **предварительный расчёт** и дождитесь его завершения.
5. Изучите предупреждения, пропущенные дни, доступные показатели и объём строк.
6. Установите флажок подтверждения замены существующих агрегатов.
7. Нажмите **«Записать агрегаты»** и проверьте итог каждого дня.

Пример диапазона **05.11.2026 → 06.11.2026** обрабатывает только 5 ноября.
Текущий и будущие незавершённые дни исключаются. Интерфейс ограничивает
запрос диапазоном до 366 дней; для первой проверки выбирайте одни сутки.

Preview читает и рассчитывает, но не заменяет витрины. Для apply нужен
успешный preview той же версии профиля и точного диапазона с актуальной
подписью структуры. Активация профиля для ручного расчёта не обязательна.

### 5.2. Почему кнопка записи не активна

Проверьте:

- завершился ли preview успешно и есть ли в нём доступные для обработки дни;
- совпадают ли профиль и обе границы с успешным preview;
- установлен ли флажок замены;
- нет ли выполняющегося задания, мешающего действию;
- не изменилась ли структура источника после проверки.

Ранее сохранённый успешный preview может быть найден в журнале для того же
диапазона. Изменение даты само по себе не запускает новую валидацию.
При сомнениях выполните новый preview, а не меняйте `validated`/signature SQL-запросом.

### 5.3. Дубликаты, NULL и ошибки

| Ситуация | Поведение текущего writer |
| --- | --- |
| Полностью одинаковые повторные записи | Не получают дополнительный вес |
| Разные измерения одного устройства с одной меткой времени | Усредняются по метрикам до 10-секундных окон |
| Частичные фазы в разных записях | Не объединяются в вымышленную полную мощность |
| NULL/NaN/бесконечность отдельной метрики | Метрика неизвестна; другие доступные измерения сохраняются |
| Корректный измеренный ноль | Остаётся нулём в потреблении/энергии |
| Мало данных, нерегулярный интервал, много дубликатов | Предупреждение, не причина блокировать весь день |
| Прибор ничего не прислал | Для его имени из справочника создаются NULL-строки с нулевыми counts |
| Источник успешно прочитан и пуст | День может заменить прежние значения NULL-строками |
| Сбой чтения/ошибка дня | Прежние строки этого дня сохраняются; не выдавать сбой за пустые данные |

Для каждого ожидаемого имени успешно прочитанного дня создаются **24 часовых
и одна суточная строка**. Суточная витрина содержит отдельную запись каждого
прибора: взвешенные средние, суммы энергии и counts, а не одну общую строку здания.

Имена берутся из настроенного справочника профиля. Сейчас writer не ограничивает
его типом устройства. Поэтому 181 ожидаемое имя и 49 фактически приславших
электрические показания — разные показатели; не добавляйте фильтр по названию
для искусственного совпадения этих чисел.

Обязательны время и ID. Отсутствующие обязательные столбцы, неверные типы,
неоднозначные mappings, неизвестные устройства и пустые ID — ошибки целостности.
NULL времени проверяется по источнику, поскольку такую строку невозможно
надёжно отнести к дню. Эти проверки не следует отключать ради успешного статуса.

Проверки качества/целостности/тайм-ауты конкретного дня могут дать
`day_skipped`: замена откатывается, обработка следующих дней продолжается.
Инфраструктурный сбой может завершить задание ошибкой. Если ни один день
не обработан, всё задание не считается успешным. Успех с предупреждениями
требует просмотра пропущенных дат.

### 5.4. Что именно хранится в витринах

- `points_count` — уникальные исходные временные метки, а не число пакетов/окон.
- `<metric>_count` — количество корректных значений данной метрики.
- Средние за сутки используют counts соответствующей метрики.
- `available_energy_kwh` — только известные вклады мощности за известные
  интервалы, без достраивания отсутствующих участков.
- `energy_kwh` — полная энергия; если она не определена, остаётся NULL.

Доступная энергия не подменяет полную в аналитике и уведомлениях.
Сумма только известных участников не должна называться полным потреблением.
Legacy counts могут оставаться NULL до подтверждённого пересчёта.

Обе витрины заменяются **одной транзакцией на день** с target-блокировками.
Повторный apply идемпотентен относительно тех же данных: выбранные дни
заменяются, а не дописываются второй копией. Это также означает, что
пересекающийся диапазон может заменить старые значения, включая замену на NULL.

## 6. Автоматическое расписание

На вкладке **«Расписание и история»** проверьте активный профиль,
границы прогресса и включение обработки. Для нового профиля:

1. Выполните успешный preview.
2. Нажмите **«Активировать проверенную версию»**.
3. Отдельно включите расписание и настройте повтор.
4. Проверьте реально появившееся scheduled-задание и его `plan.algorithm_version`.

Планировщик работает внутри adapter, отдельный системный cron не нужен.
При обычной работе после московской полуночи он ставит обработку завершённых
суток. После простоя ставит диапазон от сохранённой границы сканирования
до сегодняшней даты; у нового профиля без прогресса начинает со вчерашних суток.

`repeat_minutes=15` означает **один дополнительный суточный слот после 00:15**,
а не пересчёт каждые 15 минут в течение дня. Если сервис включён позже этого
времени, соответствующий слот может появиться сразу. Значение 0 отключает повтор.
Слоты уникальны для профиля и календарной даты.

| Поле | Значение |
| --- | --- |
| `attempted_until` | До какой исключающей границы автоматический сканер рассмотрел дни, включая пропущенные |
| `processed_until` | Исключающая граница непрерывной успешной записи, до первого незакрытого пропуска |
| `day_results` | Последний исход обработки каждого дня: `written` или `skipped` |

Пример: `processed_until=2026-11-06` означает успешную непрерывную запись
до начала 6 ноября, то есть включает 5 ноября.

Пропущенный день не должен навсегда останавливать сканирование следующих.
После устранения причины восстановите его вручную через preview/apply;
это может закрыть разрыв непрерывного прогресса. Сам по себе явный ручной
диапазон не инициализирует автоматический прогресс нового профиля.
Не переносите границы прямым UPDATE.

При `psycopg.OperationalError` scheduled-задание повторяется до пяти попыток
с паузой 5 минут. После исчерпания попыток выясните причину и проверьте
пропущенный диапазон. Приложение не может гарантировать запись при недоступном
источнике; старые агрегаты при неудачном чтении должны сохраняться.

На обновлении ВМ42 от 06.11 фактически проверены суточный и повторный слоты,
алгоритм 3/control v2, запись 4344 часовых и 181 суточной строки за 05.11.
Это историческая проверка; она не доказывает состояние расписания сегодня.

## 7. Журналы и проверка результата

### 7.1. Где смотреть

В интерфейсе блок **«Задания»** показывает последние 50 работ.
Нажмите дату создания для деталей, затем раскройте **«Подробный журнал»**.
Важны события `plan`, `quality`, `day`, `day_skipped`, `summary`, состояние
и число попыток, а не только зелёный общий статус.

Журнал хранится в БД: `jobs.events`, до 800 последних событий на задание.
`day_results` хранит последний результат дня, а не всю историю изменений.
Ни один из этих журналов не хранит предыдущие версии строк витрин для отката.

Пример проверки штатного namespace ВМ42 из Linux shell, после определения `compose`:

```sh
compose exec -T db psql -U postgres -p 25433 -d student -v ON_ERROR_STOP=1 <<'SQL'
BEGIN TRANSACTION READ ONLY;
SELECT enabled, repeat_minutes, schema_version FROM adapter_control.settings;
SELECT id, active, validated, processed_until, attempted_until
FROM adapter_control.profiles WHERE active;
SELECT id, kind, status, date_from, date_to, attempts, created_at, error
FROM adapter_control.jobs ORDER BY created_at DESC LIMIT 10;
SELECT profile_id, day, outcome, hourly_rows, daily_rows, reason
FROM adapter_control.day_results WHERE outcome='skipped' ORDER BY day DESC LIMIT 20;
COMMIT;
SQL
```

Для workstation нужна её собственная схема из `LOCAL_ADAPTER_CONTROL_SCHEMA`.
Не принимайте серверные задания за результат локального worker.

### 7.2. Проверка самих витрин

Пример одних суток — 05.11.2026:

```sh
compose exec -T db psql -U postgres -p 25433 -d student -v ON_ERROR_STOP=1 <<'SQL'
BEGIN TRANSACTION READ ONLY;
SELECT count(*) AS hourly_rows, count(DISTINCT sensor_name) AS devices
FROM student_schema.electricity_sensor_readings_hourly
WHERE bucket_start >= TIMESTAMPTZ '2026-11-05 00:00:00+03'
  AND bucket_start < TIMESTAMPTZ '2026-11-06 00:00:00+03';
SELECT count(*) AS daily_rows, count(DISTINCT sensor_name) AS devices,
       count(energy_kwh) AS known_full_energy,
       count(available_energy_kwh) AS known_available_energy
FROM student_schema.electricity_sensor_readings_daily
WHERE bucket_start = DATE '2026-11-05';
COMMIT;
SQL
```

Ожидаемый объём — 24×M часов и M суток для успешно обработанного дня,
где M — фактический справочник данного профиля. Число 181 не константа.
Проверяйте также реальные значения/counts, NULL, энергию и контрольную
выборку сырья; число строк и HTTP 200 не доказывают корректность формул.

## 8. Отчёт состояния датчиков

Reader отчёта отделён от writer-очереди и работает только на чтение.
В нём участвует весь каталог со стабильными ID, включая климат и meteo,
чьи данные нельзя оценивать по отсутствию электрических агрегатов.

Профиль выбирается через `ENERGY_AVAILABILITY_PROFILE_ID` либо активный
проверенный профиль текущей control-схемы. Явный ID сам по себе не активирует
writer и расписание. После смены алгоритма нужен актуальный fingerprint;
ID workstation нельзя копировать в namespace ВМ вслепую.

Для текущей ВМ42 в приватном env используется:

```dotenv
ENERGY_AVAILABILITY_SOURCES={"climate":{"connection":"directory"},"meteo":{"connection":"directory"}}
```

Это существующий alias читателя с SELECT к соответствующим таблицам;
электрический `fdw_reader` не имеет всех этих прав. По умолчанию таблицы —
`public.climate_sensor_data` и `public.meteo_sensor_data`. Серверные overrides
допускают `table`, `connection`, `source_timezone`; пользователь их не задаёт.

Параметры обработки: одно фоновое чтение, до трёх незавершённых проверок
периодов, до 120 секунд на SQL и 600 секунд на весь отчёт.
HTTP возвращает `pending/ready/partial/error/busy`, UI опрашивает примерно
каждые 3 секунды. Кеш готового ответа — до 10 минут; суточные статистики
переиспользуются ограниченное время. Явное обновление возможно не чаще
30 секунд после завершения и обходит переиспользование суточных данных.

`partial`/ошибка источника означает **unknown**, а не выдуманное нулевое
количество измерений. Кеш находится в памяти; перезапуск его сбрасывает.
Он не сохраняется в jobs, не меняет агрегаты и не имеет собственной ORM-миграции.

Согласованное исключение NULL/NaN/Infinity/**0** действует только в этом отчёте.
Исторический эталон, пригодность измерений и пример интерпретации описаны в
[руководстве пользователя](USER_GUIDE.md#4-отчёт-состояние-датчиков).
Это оценка относительного количества измерений, не физический диагноз приборов.

## 9. Уведомления и почта

`notifications` — отдельный процесс `run_notifications` на образе backend.
Пользователь включает правило явно. Предварительный просмотр не отправляет
писем и не сохраняет настройки; не используйте его как доказательство работы worker.

Настройки SMTP задаются в приватном `deploy/vm42/app.env`, например:

```dotenv
EMAIL_HOST=smtp.example.org
EMAIL_PORT=587
EMAIL_HOST_USER=alerts@example.org
EMAIL_HOST_PASSWORD=<пароль-приложения>
EMAIL_USE_TLS=1
EMAIL_USE_SSL=0
DEFAULT_FROM_EMAIL=alerts@example.org
```

Это шаблон: подставьте параметры предоставленного сервера. Для implicit SSL
обычно используется 465 и `EMAIL_USE_SSL=1`, `EMAIL_USE_TLS=0`; одновременно
два режима не включать. Получатель берётся из email учётной записи пользователя.

После смены env пересоздайте backend и notifications с сохранением данных;
учтите особенности Compose v1 из раздела обновления. Проверьте журнал worker,
предупреждение SMTP в интерфейсе и доставку согласованному тестовому получателю.
Без отдельного разрешения не используйте всех пользователей для тестовой рассылки.

Новые правила сравнивают полную почасовую энергию с кривой прошлых сопоставимых
дней; legacy-отчёты сохраняют прежний смысл. Не подставляйте доступную энергию
вместо полной ради устранения «Недостаточно данных».

Отчёт новой кривой уникален по пользователю/дню/версии настройки. Оперативный
отчёт обновляется, письмо — не чаще одного на день и версию. Финальные снимки
не переписываются обычным поздним пересчётом агрегатов.
Для старого правила нужны минимум 7 полных дней в предшествующих 30.

Ошибки подключения SMTP допускают до пяти попыток через 15 минут.
Неоднозначная передача — «Доставка неизвестна» — автоматически не повторяется,
чтобы не создавать дубликат. Проверяйте SMTP-журнал перед ручным повтором.
Принятие SMTP-сервером не равно доставке во входящие.

## 10. Обновление приложения

### 10.1. До обновления

1. Зафиксируйте установленную версию/образы, активный профиль, расписание,
   прогресс и незакрытые пропуски.
2. Выключите расписание; дождитесь завершения текущей записи и согласуйте
   остановку других writer, использующих те же витрины.
3. Сделайте согласованную резервную копию БД, кода, env/ключей и постоянных томов.
4. Подготовьте комплект adapter/backend/analytical/frontend одной версии.
5. Изучите необходимые ORM-миграции и явные additive upgrades.

Не распаковывайте обновление поверх приватных настроек ВМ с файлами другого ПК.
Избегайте общего `docker system prune`, `down -v`, удаления БД и копирования
локальной очереди/профиля вместо серверного.

### 10.2. Frontend и образы

Base/VM Dockerfile берёт **готовый архив**, а не собирает изменённые JSX.
На машине разработки из `Фронт/smart_energy/`, Node.js 22.12+:

```powershell
npm ci
npm run lint
$env:VITE_API_URL = '/api'
npm run build
tar -czf frontend-dist.tar.gz -C dist .
```

Поставляйте архив вместе с исходниками. Workstation Dockerfile собирает
React сам, но это не обновляет архив VM-поставки.

На ВМ, после доставки кода и резервной копии:

```sh
compose build adapter backend analytical frontend
compose stop adapter notifications
compose run --rm --no-deps adapter upgrade-aggregates
compose run --rm --no-deps adapter upgrade-control
```

`upgrade-aggregates` добавляет nullable-счётчики/доступную энергию в существующие
витрины. `upgrade-control` подготавливает control v2 до worker.
Они не пересчитывают историю. `serve` не должен создавать схему сам.

Если на этой ВМ сборка не может разрешить PyPI, используйте сохранённый
build-only overlay, как при обновлении 06.11:

```sh
docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env \
  -f docker-compose.vm42.yml \
  -f deploy/vm42/updates/release-20261106/build-network.yml \
  build adapter backend analytical frontend
```

Файл существует в проекте той ВМ; это не обязательная настройка любого сервера.
Не меняйте firewall/настройки Docker daemon как рутинный шаг обновления.

### 10.3. Замена контейнеров и контроль

Для текущего Compose v1 1.29.2 последовательность обходит `ContainerConfig`
и удаляет только контейнеры приложения, сохраняя БД/туннель/тома:

```sh
compose stop frontend backend analytical adapter notifications
compose rm -f frontend backend analytical adapter notifications
compose up -d --no-build backend analytical adapter frontend
compose up -d --no-build notifications
compose ps
```

Backend применяет ORM-миграции согласно VM Compose. Не включайте создание
индексов энергетических таблиц как обычный startup-fix.
Альтернатива после подготовки образов — обновлённый `sh deploy/vm42/start.sh`:
он сам выполняет остановку writer и явные upgrades перед запуском.

После обновления проверьте вход, обычного пользователя, Admin, графики,
NULL/реальные нули, отчёт датчиков, внутренние health и новые задания.
При смене fingerprint создайте новую версию профиля и свежий preview.
Только затем активируйте нужную версию и восстановите согласованное расписание.

Пересчитывайте только согласованную историю. Обновление программы само
не устраняет старые пропуски и не подтверждает качество legacy-строк.

## 11. Резервное копирование и восстановление

### 11.1. Что сохранять

- Дамп всей БД `student`: ORM, миграции, обе витрины, control-состояние.
- Отдельную control-БД, если `ENERGY_ADAPTER_CONTROL_DSN` указывает на другую БД.
- Код/точный комплект выпуска, frontend-архив, имена и ID образов.
- Приватные env, SSH/TLS-файлы, ключ Django/JWT.
- Если используется реестр подключений — зашифрованный файл/том и отдельный Fernet-ключ.
- Состояние активного профиля, расписания, прогресса и пропущенных дат.

Дамп PostgreSQL не включает ключ из Docker-тома Django. Потеря ключа
потребует повторного входа пользователей; потеря Fernet-ключа лишает доступа
к зашифрованному реестру.

### 11.2. Пример копии внутри проекта ВМ

Выполнять в **Linux shell ВМ**, после согласования остановки writer/notifications.
`compose` — функция из раздела 3. Архивы приватны и не включаются в Git.
Для автоматического выполнения поместите команды в отдельный сценарий
с `set -eu` в начале, чтобы остановиться при первом сбое.

```sh
umask 077
stamp=$(date +%Y%m%d-%H%M%S)
backup="deploy/vm42/backups/maintenance-$stamp"
mkdir -p "$backup"
compose stop adapter notifications
compose exec -T db pg_dump -U postgres -p 25433 -d student -Fc > "$backup/student.dump"
compose exec -T db pg_restore -l < "$backup/student.dump" > "$backup/student.contents"
tar -czf "$backup/private.tar.gz" deploy/vm42/app.env deploy/vm42/.env deploy/vm42/secrets deploy/vm42/ssl
compose exec -T backend sh -c 'cat /run/smart-energy/django_secret_key' > "$backup/django_secret_key"
sha256sum "$backup/student.dump" "$backup/private.tar.gz" "$backup/django_secret_key" > "$backup/SHA256SUMS"
```

После **каждой** команды проверьте код завершения; при автоматизации используйте
`set -e` в отдельном shell-сценарии. Пустой/нечитаемый дамп не является копией.
Список `pg_restore -l` проверяет читаемость архива, но полноценная проверка
восстановления требует отдельной тестовой БД. Код и образы сохраняются дополнительно.

После обслуживания верните сервисы и прежнее согласованное расписание:

```sh
compose up -d --no-build adapter notifications
```

Эта команда не включает выключенное через интерфейс расписание автоматически.
Копию нужно также хранить вне единственного диска ВМ по принятому порядку организации.

### 11.3. Восстановление и откат

Сначала восстановите дамп в отдельное изолированное назначение и проверьте
таблицы, пользователей, витрины, control-версию и счётчики строк. Не направляйте
тестовый restore в рабочую БД или исходник ВМ50.

Для рабочего переключения остановите writer и уведомления, согласуйте
допустимую потерю данных после момента копии, подготовьте совместимые образы,
верните нужные секреты/ключи и только после сверки включайте обработку.
При новых пользовательских данных нельзя без согласования заменять всю `student`
старым дампом; нужен перенос затронутой части из проверенной копии.

Возврата одних старых образов может быть недостаточно: control v2 и старый
worker несовместимы. Nullable-колонки витрин можно сохранить, разрушительный
downgrade не нужен. Подробная последовательность конкретного выпуска —
[AGGREGATION_UPDATE.md](../deploy/vm42/AGGREGATION_UPDATE.md).

## 12. Диагностика и регулярный контроль

### 12.1. Команды на ВМ

После определения `compose`:

```sh
compose ps
compose logs --tail=100 frontend backend analytical adapter source-db notifications
df -h .
```

Внутренний health adapter требует токен. Для проверки без вывода секрета:

```sh
compose exec -T adapter python - <<'PY'
import json, os, urllib.request
request = urllib.request.Request(
    'http://127.0.0.1:18002/health',
    headers={'X-Internal-Token': os.environ['ENERGY_ADAPTER_TOKEN']},
)
with urllib.request.urlopen(request, timeout=10) as response:
    state = json.load(response)
print({key: state.get(key) for key in ('algorithm_version', 'control_schema')})
PY
```

Ожидание этой версии на ВМ: алгоритм 3, `adapter_control`.
Health подтверждает HTTP-сервис, но не владение writer лидерской блокировкой
и не успешную обработку. Нужны реальные свежие задания с правильным `plan`.
Не завершайте неизвестный worker ради освобождения блокировки.

### 12.2. Типовые неисправности

| Симптом | Проверка и действие |
| --- | --- |
| Сайт не открывается извне | Проверить туннель на ПК, порт и SSH к ВМ42; затем frontend ВМ |
| 502 от Nginx | Состояние/журнал backend, миграции и доступ к БД |
| 403 на `/aggregation` | Вход активного пользователя и `is_staff`; для прямого HTTPS также правила Nginx |
| Admin CSRF | Совпадение origin с HTTPS-адресом и портом; cookies и proxy-настройки |
| Суточный запуск не появляется | Активный validated-профиль, enabled, границы прогресса, правильный control namespace, реальный лидер |
| Preview есть, записи нет | Проверить вид задания: preview ничего не записывает; проверить apply и его по-дневные события |
| Ошибка «слишком много дубликатов» блокирует день | Проверить версию фактически выполнившего worker и namespace; algorithm 3 трактует это как предупреждение |
| Дни пропущены, хотя общее задание успешно | Смотреть `day_skipped`/`day_results`, исправить причину и выполнить ручной repair |
| `Host is unreachable`, `Operation timed out`, `Connection refused` к источнику | Журнал `source-db`, соединение ВМ42 → ВМ50, затем повтор чтения после восстановления |
| Отчёт датчиков всё время pending | Чтение истории, лимиты времени, доступность и права трёх raw-источников |
| Все устройства unknown | Проверенный профиль/fingerprint, доступ каталога, ошибки источников; не считать это молчанием всех приборов |
| Уведомления без писем | Флаг личного правила, worker, SMTP, полная энергия/история и состояние доставки |
| В Docker остался старый экран | Согласованность frontend-архива, образа и `Ctrl+F5` |

На обновлении 06.11 наблюдались реальные обрывы туннеля ВМ42 → ВМ50.
Контейнер мог снова стать healthy между проверками, пока длительный отчёт
уже завершался partial. Проверяйте время ошибок и фактическое чтение источника.
Не выдавайте сетевой сбой за пустой день с разрешением стереть прежние значения.

### 12.3. Что проверять ежедневно

1. Есть ли успешная запись предыдущих завершённых суток и сколько дней пропущено.
2. Продвигаются ли обе границы прогресса и совпадают ли они при отсутствии разрывов.
3. Есть ли ожидаемые строки обеих витрин, реальные counts/значения и понятные NULL.
4. Доступны ли источники, нет ли повторяющихся SSH/SQL-ошибок.
5. Работает ли notifications, нет ли неопределённой доставки или очереди ошибок.
6. Достаточно ли места на диске, свежи ли резервные копии, проверяется ли восстановление.

При обычной остановке используйте `compose stop`. Не удаляйте тома с данными.
Запуск и диагностика этого проекта не требуют очистки посторонних контейнеров.
