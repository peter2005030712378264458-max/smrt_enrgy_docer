# Инструкция по установке Smart Energy

Документ описывает текущую контейнерную версию проекта. Команды выполняются
из корня репозитория, если перед примером не указан другой каталог.
Примеры для ПК приведены для Windows PowerShell, для ВМ — для Linux shell.

Смежные документы: [пользователь](USER_GUIDE.md), [администратор](ADMIN_GUIDE.md),
[содержание комплекта](README.md).

## 1. Выбор способа запуска

| Ваша задача | Что использовать | Где работает приложение |
| --- | --- | --- |
| Открыть уже установленный сайт | Браузер; из внешней сети — SSH-туннель | На ВМ42 |
| Запустить текущие исходники на своём ПК | `docker-compose.local.yml`, проект `smart-energy-workstation` | На ПК; базы остаются на ВМ |
| Установить или восстановить серверное развёртывание | `docker-compose.vm42.yml`, проект `smart-energy-vm42` | На Linux-ВМ |

Эти сценарии не нужно выполнять подряд. Для обычной работы пользователя
достаточно первого. Не объединяйте VM Compose с локальными Compose-файлами.

Существующая ВМ42 уже обновлена 06.11.2026. При повторном запуске её не нужно
заново конфигурировать или переносить БД. Фактический состав обновления описан
в [отчёте](../deploy/vm42/RELEASE_20261106.md).

### 1.1. Из каких частей состоит приложение

| Сервис | Назначение |
| --- | --- |
| `frontend` | HTTPS, интерфейс React, передача API-запросов в Django |
| `backend` | Вход, пользователи, API дашборда, настройки и отчёты |
| `analytical` | Статистическое сравнение периодов |
| `adapter` | Чтение сырья, пересчёт агрегатов, расписание и отчёт датчиков |
| `notifications` | Фоновая проверка правил и отправка писем |
| `source-db` на ВМ / `ssh` на ПК | Соединение с существующими базами через SSH |
| `db`, только в VM Compose | Отдельный PostgreSQL 17 приложения |

Локальный workstation-сценарий не создаёт собственный PostgreSQL. Его
пользователи, агрегаты и отчёты общие с сервером. Это необходимо учитывать
при пересчёте и изменении настроек.

## 2. Доступ к уже установленному приложению

### 2.1. Из внутренней сети

Откройте **https://193.232.208.42:8443/**. Docker на рабочем ПК не нужен.
Доступ зависит от сетевых правил организации. Войдите с учётной записью
приложения; SSH-пароль на странице входа не используется.

Сертификат текущего развёртывания самоподписанный. Получите у администратора
публичный сертификат или инструкции по доверию к нему. Приватный `nginx.key`
для работы в браузере не нужен.

### 2.2. Из внешней сети: SSH без Docker

Понадобятся OpenSSH Client и разрешённый доступ к ВМ42 по SSH. На своём ПК:

```powershell
ssh -N -L 127.0.0.1:8444:127.0.0.1:8443 collective@193.232.208.42
```

1. При первом подключении сверьте отпечаток SSH-ключа с администратором.
2. Введите SSH-пароль, если он запрошен.
3. Оставьте терминал открытым. Отсутствие вывода после подключения нормально.
4. Откройте **https://localhost:8444/** и войдите в приложение.

`Ctrl+C` завершает этот туннель. Порт 8444 выбран, чтобы не занимать 8443
локального приложения. Если нужен другой свободный порт, замените только
первое число в `127.0.0.1:8444:127.0.0.1:8443` и адрес в браузере.

### 2.3. Из внешней сети: подготовленный Docker-туннель

Нужны запущенный Docker Desktop, проект и подготовленные файлы
`deploy/vm42/.env`, `deploy/vm42/secrets/target_ssh_password`,
`deploy/vm42/secrets/known_hosts`. Получайте приватные файлы по защищённому
каналу у администратора, не из Git.

```powershell
$env:DASHBOARD_PORT = '8444'
docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml up -d --build
docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml ps
```

Откройте **https://localhost:8444/**. После первой сборки вместо `--build`
можно использовать `--no-build`. Контейнер продолжит работать после закрытия
PowerShell, пока работает Docker Desktop.

Остановка только этого доступа:

```powershell
docker compose -p smart-energy-vm42-access --env-file deploy/vm42/.env -f docker-compose.vm42-access.yml stop
```

Туннель не запускает и не обновляет само приложение на ВМ. Не запускайте два
туннеля на одном локальном порту. Для Django Admin новый адрес с портом также
должен быть разрешён в `DJANGO_CSRF_TRUSTED_ORIGINS` серверной конфигурации.

## 3. Локальная установка приложения на Windows

### 3.1. Что подготовить

- Docker Desktop в режиме Linux-контейнеров с работающим `docker compose`.
- Python 3 для сценария конфигурации.
- Git и копию этой версии проекта.
- Доступ ПК к ВМ42 по SSH; на ВМ42 должны быть доступны БД приложения
  и туннель источника к ВМ50.
- SSH-реквизиты ВМ42 и отдельные PostgreSQL-реквизиты для БД приложения
  и чтения источника/справочника.
- Сертификат и ключ для локального HTTPS.

Node.js для этого способа на ПК не обязателен: workstation Dockerfile
собирает frontend внутри контейнера Node 22.

Откройте PowerShell в каталоге проекта. Для текущей рабочей копии:

```powershell
Set-Location 'C:\Users\Admin\Desktop\smart_energy_local\smrt_enrgy_docer'
docker version
docker compose version
python --version
```

`docker version` должен показывать и клиент, и сервер. Ошибка
`docker_engine ... The system cannot find the file specified` обычно означает,
что Docker Desktop ещё не запущен.

### 3.2. Подготовка приватных файлов

До запуска подготовьте:

| Файл | Содержимое |
| --- | --- |
| `deploy/vm42/secrets/target_ssh_password` | Пароль согласованной SSH-учётной записи ВМ42 |
| `deploy/vm42/secrets/known_hosts` | Проверенные ключи SSH-серверов; нужны записи для используемых адресов |
| `ssl/nginx.crt`, `ssl/nginx.key` | Пара сертификата и ключа для `localhost` |

Локальный туннель текущей конфигурации использует `collective@193.232.208.42`.
Если инфраструктура другая, её параметры необходимо согласованно изменить
в `deploy/local/tunnel.sh` и связанных настройках; одного нового пароля недостаточно.

Не перезаписывайте уже работающие приватные файлы. При их наличии переходите
к проверке существующей конфигурации.

Если локального сертификата ещё нет, можно создать его OpenSSL из Git for Windows:

```powershell
New-Item -ItemType Directory -Force ssl
& 'C:\Program Files\Git\usr\bin\openssl.exe' req -x509 -nodes -days 365 -newkey rsa:2048 -keyout ssl/nginx.key -out ssl/nginx.crt -subj '/CN=localhost' -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'
```

Выполняйте генерацию только при отсутствии обоих файлов. Для корпоративного
использования применяйте выданную администратором пару. Ключи не включаются в Git.

### 3.3. Создание настроек

```powershell
python deploy/local/configure.py
```

Сценарий запросит PostgreSQL-пользователей и пароли, создаст
`deploy/local/app.env`, ключ зашифрованного реестра подключений и отдельное
имя локальной очереди в корневом `.env`. Параметры баз/портов берутся также
из `deploy/local/app.env.example`; проверьте их соответствие инфраструктуре.
Источник и каталог должны быть доступны выбранному читателю с правами SELECT.

Если `app.env` уже существует, сценарий сохраняет его и завершает работу
с сообщением об этом. Это защита существующей конфигурации, а не повод удалять её.

Для уже настроенного доступа допустим альтернативный вариант:

```powershell
python deploy/local/configure.py --from-vm
```

Он читает необходимые параметры из контейнера backend ВМ42. Используйте его
только с разрешения владельца этих реквизитов. Нужны рабочий Docker,
подготовленные SSH-файлы и образ `smart-energy-ssh-tunnel`; при необходимости
сначала соберите его:

```powershell
docker compose -p smart-energy-workstation -f docker-compose.local.yml build ssh
```

### 3.4. Сборка и первый запуск

```powershell
powershell -ExecutionPolicy Bypass -File deploy/local/start.ps1
docker compose -p smart-energy-workstation -f docker-compose.local.yml ps
```

Сценарий:

1. Подготавливает уникальную служебную очередь этой установки.
2. Собирает и запускает SSH-контейнер.
3. Собирает образы приложения, включая React из исходников.
4. Явно добавляет недостающие nullable-поля витрин командой `upgrade-aggregates`.
5. Явно готовит отдельную control-схему через `adapter.local_setup`.
6. Запускает шесть локальных сервисов и открывает браузер.

Адрес по умолчанию: **https://localhost:8443/**. Django-миграции и индексы
рабочих таблиц этот локальный сценарий автоматически не создаёт. Он рассчитан
на уже подготовленную БД ВМ42, а не на пустую локальную базу.

Скопированные профили неактивны и требуют новой проверки. Локальное
расписание изначально выключено. Не включайте его параллельно с серверным
без выбора единственного ответственного writer: агрегаты у них общие.

### 3.5. Если порт 8443 занят

Сначала выясните, что занимает порт:

```powershell
Get-NetTCPConnection -LocalPort 8443 -State Listen
docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

Можно оставить существующее приложение и выбрать другой порт, например 9443:

```powershell
$env:LOCAL_HTTPS_PORT = '9443'
powershell -ExecutionPolicy Bypass -File deploy/local/start.ps1
```

Откройте **https://localhost:9443/** вручную: текущий `start.ps1` открывает
в браузере фиксированный адрес 8443. Для административных форм разрешите новый
origin в `deploy/local/app.env`. Чтобы сохранить выбор после закрытия PowerShell,
задайте `LOCAL_HTTPS_PORT=9443` в корневом `.env` без изменения других параметров.

Не удаляйте неизвестный контейнер только ради освобождения порта.

### 3.6. Повторный запуск и остановка

Если код и образы не менялись:

```powershell
python deploy/local/configure.py --isolate-control
docker compose -p smart-energy-workstation -f docker-compose.local.yml up -d
docker compose -p smart-energy-workstation -f docker-compose.local.yml ps
```

После изменений кода используйте `deploy/local/start.ps1` для сборки и явных
подготовительных шагов. Остановка:

```powershell
docker compose -p smart-energy-workstation -f docker-compose.local.yml stop
```

Обычная остановка не требует `down -v`. Локальные тома хранят ключ сессий
и зашифрованный реестр дополнительных подключений.

## 4. Установка серверного варианта на Linux-ВМ

### 4.1. Границы штатной процедуры

Поставляемая конфигурация привязана к инфраструктуре ВМ42/ВМ50. Первоначальный
`migrate.sh` переносит существующее приложение из БД `student` на ВМ50
в новую пустую `student` на ВМ42. Это **перенос существующей установки**,
а не универсальный установщик на полностью пустые источники.

Если нет исходной БД `student`, справочников или таблиц витрин, потребуется
отдельно подготовить согласованную структуру. `upgrade-aggregates` только
дополняет существующие таблицы; он не создаёт всю предметную БД.
Не запускайте `agg_taables.sql` как автоматическую миграцию.

Для уже работающей ВМ42 пропустите первоначальную конфигурацию и перенос.
Обновление выполняйте по [руководству администратора](ADMIN_GUIDE.md#10-обновление-приложения).

### 4.2. Требования и параметры

Нужны Linux, Docker Engine, Compose, разрешённый доступ к Docker,
свободные порты приложения и SSH-доступ к ВМ50. На машине подготовки
также нужны Python 3, OpenSSH с `ssh-keyscan` и OpenSSL.

| Порт на ВМ42 | Привязка | Назначение |
| --- | --- | --- |
| 8443 | По VM Compose — `0.0.0.0` | HTTPS Nginx |
| 25433 | `127.0.0.1` | PostgreSQL 17 приложения |
| 25432 | `127.0.0.1` | SSH-туннель к PostgreSQL ВМ50 |
| 15000 | `127.0.0.1` | Django |
| 18001 / 18002 | `127.0.0.1` | Аналитика / adapter |

Рабочая папка текущей ВМ: `/home/collective/smart-energy-vm42`.
ВМ использует host networking. Не заменяйте существующий PostgreSQL
10/CMDBuild на системном порту 5432.

### 4.3. Однократная подготовка новой установки

На машине подготовки, в чистой копии проекта без прежних приватных настроек:

```powershell
python deploy/vm42/configure.py
```

Сверьте выведенные SSH-отпечатки с администратором и введите отдельно
реквизиты SSH, чтения сырья, справочников, исходной БД приложения и пароль
нового PostgreSQL. Сценарий создаёт:

- `deploy/vm42/.env` — параметры Compose;
- `deploy/vm42/app.env` — параметры сервисов и внутренние токены;
- `deploy/vm42/secrets/` — приватные файлы и закреплённые SSH-ключи;
- `deploy/vm42/ssl/` — пару HTTPS, если её ещё нет;
- `deploy/vm42/backups/` — каталог первоначального дампа.

Существующие настройки не перезаписываются. Проверьте hosts/origins, адреса,
права на файлы и политику `deploy/vm42/https-allow.conf`. В текущем временном
режиме последняя директива — `allow all`; тогда ограничение внешнего доступа
должно обеспечиваться сетью организации.

### 4.4. Подготовка образов и доставка

На машине с Docker и доступом к зависимостям:

```powershell
docker compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml build
docker pull postgres:17-alpine
docker save -o vm42-images.tar smart-energy-vm42-backend smart-energy-vm42-analytical smart-energy-vm42-adapter smart-energy-vm42-frontend smart-energy-ssh-tunnel postgres:17-alpine
```

VM frontend распаковывает поставляемый `frontend-dist.tar.gz`. Если React
меняли, архив сначала нужно обновить по [процедуре упаковки](ADMIN_GUIDE.md#102-frontend-и-образы).

Доставьте согласованный комплект кода, приватные VM-файлы и архив образов
по SSH внутрь каталога проекта ВМ. Не переносите чужие локальные `.env`,
`node_modules`, `.venv`, `.git`, пользовательские CSV и workstation-идентификатор
очереди. Для действующей установки сохраните её собственные секреты и настройки.

На ВМ из каталога проекта:

```sh
docker load -i vm42-images.tar
sh deploy/vm42/start.sh
```

При первом запуске сценарий поднимает БД/туннель, переносит данные только
в пустое назначение, выполняет `upgrade-aggregates` и `upgrade-control`,
запускает сервисы. Backend применяет ORM-миграции.
Маркер `deploy/vm42/backups/restore-complete` предотвращает повторный перенос.
Не создавайте этот маркер вручную для обхода ошибки восстановления.

Если назначение уже содержит данные или есть предыдущий дамп, перенос
откажется продолжать. Сохраните файлы и выясните состояние; не удаляйте БД.

### 4.5. Первый вход и первый расчёт

1. Откройте сайт и войдите перенесённой учётной записью.
2. При отсутствии администратора создайте суперпользователя:

   ```sh
   docker-compose -p smart-energy-vm42 --env-file deploy/vm42/.env -f docker-compose.vm42.yml exec backend python manage.py createsuperuser
   ```

3. В `/admin/` назначьте ответственному оператору статус персонала.
4. В «Источники и агрегации» сохраните новую версию профиля, подтвердите
   соответствия/единицы/интервал, выполните предварительный расчёт одного дня.
5. После проверки запишите этот диапазон и убедитесь в заполнении витрин.
6. Активируйте проверенную версию и отдельно включите расписание.

После первоначального переноса старые профили неактивны и непроверены,
расписание выключено. Не включайте их прямым SQL. На действующей ВМ42
профиль и расписание уже были подготовлены обновлением 06.11.

Флаг `ENERGY_USE_STORED_ENERGY` должен совпадать в Django и аналитике.
На действующей ВМ он равен 1; новая установка требует проверки истории
перед переходом с legacy-режима. Не меняйте этот флаг для устранения пустого графика.

### 4.6. Особенности повторного запуска

`sh deploy/vm42/start.sh` использует уже собранные образы; он не скачивает
новый код и не пересобирает его без `VM42_BUILD=1`. На Compose v1 сценарий
пересоздаёт контейнеры приложения, сохраняя БД и тома. На это время сайт прерывает работу.

Если сайт уже работает, пользователю достаточно открыть его или запустить
свой туннель. Запускать `start.sh` при каждом входе не требуется.

На этой ВМ обычная build-сеть ранее не разрешала PyPI. Для сборки был
применён отдельный `build.network: host` overlay внутри проекта;
точная команда приведена в [отчёте выпуска](../deploy/vm42/RELEASE_20261106.md).

## 5. Проверка результата установки

Установка считается готовой к работе после следующих проверок:

1. Все ожидаемые сервисы запущены; БД и SSH-туннель доступны.
2. Главная страница и `/admin/login/` загружаются через выбранный HTTPS-адрес.
3. Можно войти и выйти обычной учётной записью.
4. На дашборде загружаются фильтры и реальные значения выбранной даты;
   неизвестные показатели отображаются как пропуски.
5. У обычного пользователя есть отчёт состояния датчиков, но нет управления пересчётом.
6. У оператора проходит preview; после разрешённой записи появляются
   часовые и суточные строки. HTTP health без такой проверки недостаточно.
7. Недельный график имеет семь календарных позиций; пропуски допустимы,
   если соответствующих данных действительно нет.
8. Для фоновых задач проверены активный профиль, расписание и свежие задания.

Первое чтение истории для отчёта датчиков может занимать несколько минут.
`unknown` из-за ошибки источника не является доказательством, что датчик молчит.

## 6. Типовые проблемы установки

| Симптом | Действие |
| --- | --- |
| Docker daemon недоступен | Запустить Docker Desktop и дождаться готовности |
| `Bind ... 8443 ... port is already allocated` | Найти владельца порта или выбрать `LOCAL_HTTPS_PORT` / `DASHBOARD_PORT` для нужного сценария |
| `Configuration already exists` | Использовать сохранённые приватные настройки; не удалять их автоматически |
| SSH host key verification failed | Сверить ключ с администратором и обновить нужную запись `known_hosts` |
| `source-db` не подключается | Проверить доступ ВМ42 к SSH ВМ50 и реквизиты; смотреть журналы проекта |
| На странице 502 | Проверить backend и зависимые сервисы, затем их журналы |
| Django Admin сообщает CSRF | Проверить точный HTTPS origin, включая порт, в используемом env |
| После изменения React старый экран | Для VM-поставки обновить frontend-архив, пересобрать образ, затем обновить браузер |
| Данные есть в сырье, но график пуст | Проверить наличие рассчитанных витрин и выбранный период; запуск контейнеров сам по себе историю не пересчитывает |

Дальнейшее обслуживание: [руководство администратора](ADMIN_GUIDE.md).
