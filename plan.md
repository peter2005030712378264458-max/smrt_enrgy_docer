# План: пересчёт агрегатов по доступным данным

Статус: утверждён пользователем; реализован и проверен в fix/available-energy-aggregates.
Основание: [spec.md](spec.md), ответы пользователя от 05.11.2026.
Планирование разрешено пользователем. Согласованы D1 (окна 10 секунд и
усреднение повторов одного времени), D2 (сохранение энергии по доступным
измерениям) и D3 (NULL-строки по полному справочнику профиля).
План и итоговая спецификация подтверждены; разрешена реализация в отдельной ветке.

## 1. Архитектура

Сохранить существующий адаптер и его стандартный HTTP-сервер. Не добавлять
отдельный сервис, очередь или иной фреймворк. PostgreSQL выполняет нормализацию
и свёртку; Python получает агрегированные статистики, рассчитывает результаты
и транзакционно заменяет обе витрины за день.

Поток обработки:

```text
Профиль + завершённый диапазон
  → обязательная проверка структуры, единиц и соответствий
  → цикл по московским суткам
      → чтение исходных строк в согласованном снимке
      → нормализация значений и удаление точных повторов
      → среднее повторов одного времени → среднее 10-секундного окна
      → часовые статистики доступных метрик
      → NULL для отсутствующих показаний по D3
      → суточные средние по счётчикам метрик, энергия по D2
      → preview: результат без записи витрин
      → apply: атомарная замена часовых и суточных строк
      → сохранение результата дня и прогресса
    при локальной ошибке дня → записать пропуск и продолжить
    при общей неисправности → остановить задание с явной ошибкой
```

## 2. Согласованные решения

| Решение | Подтверждённое поведение | Влияние на реализацию |
| --- | --- | --- |
| D1: согласовано | Окна 10 секунд на датчик; среднее повторов одного времени, затем среднее окна; одинаковые повторы не увеличивают вес | SQL, статистики, формула энергии, профиль, live-чтение |
| D2: согласовано | Сохранять энергию по доступным измерениям; неизвестный полный итог не подменять частичным | Модель, явное обновление схемы, Django, аналитика, уведомления, подписи UI |
| D3: согласовано | Все счётчики из справочника профиля, включая полностью отсутствующих в показаниях; каждому 24 часовые и одна суточная строка | Состав счётчиков, NULL-строки и замена пустого дня |

Технический контракт: добавить `available_energy_kwh` в часовую и суточную
витрины. Существующий `energy_kwh` сохраняет смысл полной энергии и остаётся
NULL при неизвестном полном итоге. Это позволяет хранить согласованный
доступный расход и сохраняет строгий контракт аналитики и уведомлений.
При полном наборе данных оба значения совпадают. Новое поле в legacy-строках
остаётся NULL до проверенного пересчёта; не заполнять его догадкой при upgrade.

## 3. Нормализация и временные окна

Компоненты: `adapter/mapping.py`, `adapter/queries.py`, небольшой общий модуль
для правил нормализации/энергии при необходимости.

1. Сохранить масштабирование единиц и явную интерпретацию исходного времени.
   NULL, NaN и бесконечности не участвуют в числовых агрегатах.
2. Ключ совпадения — исходный идентификатор счётчика и точное время.
   Точные повторы определяются по нормализованным измерениям, без служебного ID
   строки/времени поступления. Число отброшенных повторов сохраняется отдельно.
3. Вычислять общую мощность каждой исходной строки из `pt` либо трёх её фаз.
   Не собирать искусственно полный набор фаз из разных конфликтующих строк.
4. Применить утверждённое D1: исключить повторный вес одинаковых строк,
   усреднить разные значения на одной метке времени, затем получить среднее
   10-секундного окна. Привязать окна к границам времени; правая граница
   исключается. NULL пропускается при усреднении; пустое окно остаётся NULL.
5. Шаг обработки хранить отдельно от подтверждённого исходного интервала
   (`sample_seconds`). Для выбранных окон 10 секунд добавить параметр шага
   в профиль и его проверку; не заменять автоматически интервал источника на 10.
   Проверять совместимость исходного интервала с выбранным шагом, границы часов
   и календарных суток. Для старого источника с шагом больше 10 секунд нельзя
   выдумывать промежуточные измерения.
6. Усреднение внутри окна не обещает уменьшения объёма чтения PostgreSQL:
   сравнить планы и время запросов на изолированном наборе.

## 4. Агрегаты, NULL и энергия

Компоненты: `adapter/model.py`, `adapter/queries.py`, `adapter/runner.py`.

- Средние каждой метрики: сумма доступных значений / её собственный count.
  Суточные средние взвешиваются этими же counts; отсутствие всех значений даёт
  NULL и нулевой count. Максимумы не получают подставленный ноль.
- `points_count` считает нормализованные уникальные моменты измерений,
  `<metric>_count` — моменты с пригодным значением соответствующей метрики
  после объединения повторов одного времени. Counts окна переносятся в часовые
  суммы/counts: при объединении средних окон использовать их корректные веса.
  Не подменять число измерений числом созданных NULL-окон или 360 окнами часа.
  Сырые количества и число окон хранятся отдельно в диагностике.
- Создать календарную сетку из 24 часов и фиксированного списка ожидаемых
  счётчиков, присоединить часовые статистики. Для отсутствующего часа записать
  строку с NULL метриками/максимумом/энергией, points_count=0 и counts метрик=0.
  Не материализовать каждую отсутствующую секунду в Python и не включать
  placeholders в суммы/counts реально полученных измерений.
- Для каждого ожидаемого счётчика сформировать и суточную строку, даже если
  все 24 часа пусты. Значения метрик/энергии остаются NULL, counts — 0.
  Наличие строки не означает наличие мощности: available_meters считает только
  пригодные значения, total_meters включает весь ожидаемый состав.
- Состав ожидаемых счётчиков читать один раз из полного справочника профиля
  до замены данных. Использовать существующие `directory_alias`/`directory_names`
  с указанными в профиле таблицей и столбцом. Справочник становится ожидаемым
  составом, а не только allowlist фактически пришедших ID. Не фильтровать список
  по последнему показанию, присутствию в диапазоне, прежним агрегатам или
  активности устройства. Сохранять независимость справочников разных профилей.
  Проверить валидность идентификаторов, устойчивое устранение повторов имён
  и ошибку чтения справочника; не трактовать сбой как пустой ожидаемый состав.
- Убрать отказы по покрытию, дубликатам, уменьшению числа строк и отсутствию
  мощности, включая отсутствие мощности у всех счётчиков. Старые параметры
  качества принимать для совместимости с явным уведомлением, что они больше
  не блокируют запись. Не вычислять процент покрытия как условие допуска.
- Энергия по доступным данным вычисляется из нормализованных пригодных
  измерений с подтверждённым исходным интервалом; усреднение повторов одного
  времени не добавляет длительности. Для регулярного ряда вклад равен
  `SUM(P_valid_w) * sample_seconds / 3600000`. В оконном расчёте эквивалентно
  использовать среднее и суммарную подтверждённую длительность известных
  измерений, а не автоматически давать каждому неполному окну все 10 секунд.
  Проверять неоднозначную частоту/перекрывающиеся интервалы: не завышать расход,
  отмечать неопределённый вклад без блокировки остальных метрик и дней.
  Пропуски не заполнять мощностью соседей, не экстраполировать доступный расход
  на весь час и не умножать исходные секундные суммы на 10.
- `available_energy_kwh` — сумма известных вкладов, NULL при отсутствии
  пригодных вкладов, 0 при известных нулевых. Для суток и группы счётчиков
  складывать доступные значения, не превращая отсутствие всех вкладов в 0.
- Если полная энергия хотя бы одного часа неизвестна, суточная полная энергия
  также неизвестна, включая полностью отсутствующие часы. Ноль энергии допустим
  при подтверждённых нулевых показаниях, а не при отсутствии данных.
- Добавить nullable numeric `available_energy_kwh` в обе витрины явным
  идемпотентным additive upgrade. Расширить writer/preflight и запросы;
  не выполнять DDL при обычном старте API и не переписывать legacy-данные.

## 5. Ошибки дня, расписание и прогресс

Компоненты: `adapter/runner.py`, `adapter/service.py`, `adapter/store.py`,
`adapter/__main__.py`.

Разделить ошибки:

| Категория | Поведение |
| --- | --- |
| Пропуски измерений, все значения мощности NULL, дубликаты | Рассчитать доступные метрики; предупреждение |
| Локальная проблема данных дня, не позволяющая безопасно сопоставить/записать результат | Откатить текущий день, записать `day_skipped`, продолжить |
| Потеря БД, неверная структура/профиль, невозможность получить блокировку | Ошибка задания; ограниченные повторы для временного технического сбоя |
| Остановка worker | Возобновление по имеющемуся протоколу; не объявлять день пропущенным |
| Неожиданная программная ошибка | Ошибка задания; не скрывать через общий `except Exception: continue` |

Успешно прочитанный пустой день при известном ожидаемом составе не является
ошибкой: записать NULL-строки для всех ожидаемых счётчиков, в том числе вместо
старых значений, и предупредить об отсутствии данных. Техническую ошибку чтения
не превращать в пустой результат. Если ожидаемый состав получить невозможно,
не выполнять NULL-замену. NULL времени, который нельзя отнести к конкретному
дню, остаётся общей ошибкой обязательных исходных полей.

Предлагаемые additive изменения служебной схемы:

- `profiles.attempted_until date`: исключительная граница рассмотренных
  автоматическим заданием дат; допускает документированные пропуски.
- `day_results`: актуальный результат по `(profile_id, day)` с исходом
  `written`/`skipped`, ID задания, временем, количеством строк и безопасным
  кодом/описанием причины. Preview не меняет результаты фактической записи.
- `processed_until` сохраняет значение непрерывной подтверждённой записи.
  Продвижение `attempted_until` не утверждает, что витрины за все даты заполнены.
  Пропуск не удаляется из учёта только потому, что следующий день успешен.

Установку выполнять явной идемпотентной командой обновления control-схемы,
проверяющей версию. Не выполнять DDL в `serve`. Для существующих профилей
начальная граница рассмотрения берётся из прежнего прогресса; историю не
сканировать и не помечать успешной автоматически. Сохранить выбор схемы
`adapter_control`/`adapter_workstation` через существующий `Store`.

Расписание использует границу рассмотрения, а обычный повтор вчерашнего дня
остаётся возможным. Старые пропуски видны и доступны ручному пересчёту;
отдельный автоматический механизм массового восстановления истории не добавлять.
Локальный результат дня сохраняется прежде продвижения границы рассмотрения.
При сбое между commit витрин и сохранением служебного результата безопасно
повторить день идемпотентно. Учесть возможный отдельный control DSN: общей
транзакции между двумя разными БД не предполагать.

Для CLI без служебной очереди сохранять список пропущенных дат и границу
рассмотрения в совместимо версионированном checkpoint; старый checkpoint не
переинтерпретировать молча. Явные диапазоны не сдвигают автоматический прогресс.

## 6. Preview, статусы и интерфейс

- Preview и запись используют один расчёт и одни предупреждения. Частично
  обрабатываемый диапазон допускается к записи; перед ней видны пропуски.
- Текущее состояние `succeeded` можно сохранить для завершённого задания,
  в котором есть записанные дни; в UI показывать «Готово с предупреждениями»
  и отдельно число записанных и пропущенных дней. Если ни один день невозможно
  записать, возвращать ошибку с понятным результатом по датам.
- При preview вместо записанных дней считать дни, готовые к записи; формальные
  `written=true` события появляются только после commit.
- Добавить итоговое событие с числами обработанных/пропущенных дней и отдельный
  доступный список текущих пропусков из `day_results`. Текущие 800 событий
  задания не должны быть единственным долговременным учётом результатов.
- Обновить тексты порогов качества и детали `QualityDetails` в
  `AggregationPage.jsx`. Не обещать полное потребление там, где доступна только
  часть мощности. Энергию по доступным измерениям показывать с явной подписью,
  сохраняя отличие от полного расхода и предупреждение о неполных данных.
- Обновить API gateway только в пределах allowlist и staff-проверок.

## 7. Потребители и совместимость

Проверить Django `dashboard_queries.py`, FastAPI period-comparison,
`apps/notifications/{energy,hourly,curve}.py` и `adapter/live.py`.

- Общая функция нормализации и правил энергии используется и для завершённых
  суток, и для read-only текущих завершённых часов; пороги покрытия в live-пути
  не должны сохранять старую семантику. Незавершённый час не включать.
- Полная энергия остаётся строгой; NULL/отсутствие часа не исчезают из итоговой
  суммы. Уведомления не принимают доступную энергию за полный расход.
- Добавить доступную энергию в контракт dashboard API и его карточек/tooltip;
  неполная мощность или энергия не скрывает известный доступный расход.
  Новое поле не подставляется вместо полной энергии в FastAPI Z-test,
  baseline уведомлений и критерии полного расхода. Проверить оба режима энергии.
- Не восстанавливать неизвестную полную энергию из средней мощности в старом
  режиме `ENERGY_USE_STORED_ENERGY=0`. В обоих режимах учитывать известность
  энергии новых агрегатов; детали проверки закрепить числовыми тестами.
  Сам флаг и рабочие настройки пользователя автоматически не переключать.
- Сохранять `available_value` и counts для мощности, вес метрик, реальные нули,
  отличия отсутствующей строки от строки с нулевым потреблением.
- Изменение семантики нормализованного ряда включить в fingerprint алгоритма/
  профиля. Для активации на ВМ нужна новая версия и свежий preview;
  старое подтверждение не считать действительным для нового алгоритма.
- Старые агрегаты за пределами выбранного диапазона не переписывать.

## 8. Валидация

Тесты добавлять рядом с существующими интеграционными и числовыми тестами,
не подменяя их проверкой только статуса. Основные сценарии перечислены
в `spec.md` и развёрнуты в T02–T10, включая T08A–T08B, файла `tasks.md`.

Проверки после реализации:

```text
python -m unittest discover -s adapter/tests -v
docker compose -p smart-energy-adapter-tests -f adapter/tests/compose.yml run --build --rm tests
python manage.py test apps.consumption apps.aggregation apps.users apps.notifications
python -m pytest
npm run test:mapping
npm run test:dashboard
npm run lint
npm run build
python -m unittest discover -s deploy/vm42 -p test_configuration.py
```

Команды запускать из каталогов соответствующих компонентов и в подходящем
окружении. Полный изолированный Compose уже включает часть проверок Python;
не дублировать без причины. Новые необходимые тесты уведомлений включить
в изолированный запуск или его существующий notification Compose.
HTTP smoke/UI fixture запускать отдельно от тестов, сбрасывающих общие фикстуры.
После изменения UI собрать с `VITE_API_URL=/api`, обновить архив и проверить
затронутую страницу. Не подключать тестовые фикстуры к рабочему PostgreSQL.

## 9. Самостоятельное обновление ВМ

Подготовить отдельную инструкцию рядом с `deploy/vm42/README.md`:

1. Определить текущую версию, Compose v1/v2, активный профиль, control-схему,
   потребителей энергии и приватные зависимости. Сопоставить с пакетом обновления;
   не считать старый отчёт точной текущей конфигурацией.
2. Сохранить резервные копии затрагиваемых агрегатов/control-данных,
   кода и меток образов, приватных настроек и ключей без вывода секретов.
3. Зафиксировать состояние расписания и остановить старый writer перед upgrade.
   Не останавливать PostgreSQL CMDBuild, не удалять тома и не заменять базу.
4. Собрать/загрузить согласованные версии компонентов; выполнить явные additive
   обновления control-схемы и витрин для `available_energy_kwh`.
   Проверить порядок операций в `start.sh`: новая control-схема должна быть
   готова до запуска worker. Не включать обычные DDL при старте API.
5. Создать новую версию профиля, подтвердить интервалы и параметры D1,
   выполнить preview выбранного завершённого дня, затем проверяемую запись.
   Проверить данные и предупреждения в SQL/API/UI, включая пропуски и NULL.
6. Только после этого активировать профиль и восстановить выбранное владельцем
   расписание. Не включать второй workstation writer в общие витрины.
7. Описать откат: остановка writer, возврат образов и согласованного состояния
   профилей/control-прогресса, а при записи нового формата — восстановление

## 11. Изоляция локального worker после проверки установки

Повторная ошибка от 05.11.2026 объясняется общей служебной схемой
`adapter_workstation`: её лидер был подключён до запуска нового контейнера.
Задание `6cfec052` выполнил старый алгоритм, без algorithm_version в plan,
хотя новый контейнер содержал исправленный SQL и отвечал на health.

Для каждой установки хранить `LOCAL_ADAPTER_CONTROL_SCHEMA=adapter_ws_v3_<ID>`
в корневом приватном `.env`. Генерация идемпотентна, остальные настройки
не перезаписываются; Compose отказывается запускаться без отдельного ID.
`start.ps1` подготавливает ID, явно обновляет целевые колонки и вызывает
`adapter.local_setup` до запуска worker. Команда переносит только совместимые
профили из старых схем как непроверенные и неактивные; задания, прогресс,
подтверждения и включённое расписание не копирует. Старые схемы не изменяются.

Во внутреннем health вернуть algorithm_version и control_schema. Проверить
разные очереди и лидерские блокировки на изолированном PostgreSQL; после
установки запустить preview 03.11 через HTTP/реальную очередь. Не вызывать
process_job напрямую и не применять результат к рабочим агрегатам.
